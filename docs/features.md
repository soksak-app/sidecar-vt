- [~] S13 — P1: Handle a request on a persistent connection as soon as it arrives after a `retain` that closes terminal sessions. Found on 2026-10-04 by core G1.4-90-4-2: after the service handled a `retain` that closed sessions, the host's next configuration and open request stayed in the kernel receive queue of the connection for about 10 s (1412 bytes by `netstat`) while every service thread was idle, and the input loop read them only when a later event woke the connection task. To measure it, the service writes `request` events `{operation, surface, owner, connection, idle_us, us}` for every request, `output_blocked` when writing an output line takes 10 ms or more, and `read_wait` `{waited_us, pending_polls, since_last_poll_us, bytes}` when a read receives data after waiting a second or more (core `docs/spec/performance-trace.md`); `request_operation` names the request kind (test `request_operation_names_the_kind_of_request`). `a_request_after_retain_closes_pty_sessions_is_handled_at_once` opens two real PTY sessions on a persistent connection, closes them with `retain` and requires the next request to be answered within 2 s; it passes 10 rounds and does not reproduce the stall yet. The stall also occurred with the current-thread runtime and with tokio 1.53.2. Measured further on 2026-10-04 with core check applications: during each stall the kqueue state of the connection socket's read filter was `KN_ACTIVE|KN_QUEUED` (`lskq`, `aq---`) for the whole 10 s, while the runtime's I/O driver waited in `kevent` through mio `Selector::select` (lldb stack of the current-thread build), so the event was on the kqueue's active list and the waiting `kevent` did not return it. The process holds three kqueue descriptors (3, 4, 5) that list the same knotes; whether they are one kqueue and the driver waited on it, or distinct kqueues, is not yet determined, because attaching lldb interrupts `kevent` and leaves its return value instead of its arguments. Measured on 2026-10-04 with the multi-thread build at the moment of a stall: the kqueue (descriptors 3, 4 and 5, one kernel object) had one queued event (`lsof` `count=1, state=0x8`) and no thread asleep on it (`lskq` kqueue status `---`, while it is `k--` with `state=0xa, count=0` in normal operation), the process used no CPU, and the runtime's driver worker was asleep in `kevent` under mio `Selector::select` for the whole `sample`. So the driver worker slept in `kevent` but not on the kqueue that held the event. `portable-pty` closes descriptors only in the forked child before `exec`. Seeing what that `kevent` waits on needs `spindump`, which runs only as root; lldb could not pause the multi-thread process. Measured on 2026-10-04 later: the PTY output is read by a blocking std thread per session (`read_output` in `vt-core/src/pty.rs`), so closing a session's PTY touches no knote of the runtime's kqueue; `a_request_after_retain_closes_pty_sessions_is_handled_at_once` passed 10 runs of 10 rounds (100 rounds) without a stall, while the stall recurred twice in the core window checks of the same day; `sudo -n` has no cached credential, so `spindump` cannot run. Retry condition: the user grants root for one `spindump` taken during a stall.
