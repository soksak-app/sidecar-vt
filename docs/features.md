- [o] S13 — P1: Handle a request on a persistent connection as soon as it arrives after a `retain` that closes terminal sessions. Found on 2026-10-04 by core G1.4-90-4-2: after the service handled a `retain` that closed sessions, the host's next configuration and open request stayed in the kernel receive queue of the connection for about 10 s (1412 bytes by `netstat`) while every service thread was idle, and the input loop read them only when a later event woke the connection task. To measure it, the service writes `request` events `{operation, surface, owner, connection, idle_us, us}` for every request, `output_blocked` when writing an output line takes 10 ms or more, and `read_wait` `{waited_us, pending_polls, since_last_poll_us, bytes}` when a read receives data after waiting a second or more (core `docs/spec/performance-trace.md`); `request_operation` names the request kind (test `request_operation_names_the_kind_of_request`). `a_request_after_retain_closes_pty_sessions_is_handled_at_once` opens two real PTY sessions on a persistent connection, closes them with `retain` and requires the next request to be answered within 2 s; it passes 10 rounds and does not reproduce the stall yet. The stall also occurred with the current-thread runtime and with tokio 1.53.2. Measured further on 2026-10-04 with core check applications: during each stall the kqueue state of the connection socket's read filter was `KN_ACTIVE|KN_QUEUED` (`lskq`, `aq---`) for the whole 10 s, while the runtime's I/O driver waited in `kevent` through mio `Selector::select` (lldb stack of the current-thread build), so the event was on the kqueue's active list and the waiting `kevent` did not return it. The process holds three kqueue descriptors (3, 4, 5) that list the same knotes; whether they are one kqueue and the driver waited on it, or distinct kqueues, is not yet determined, because attaching lldb interrupts `kevent` and leaves its return value instead of its arguments. Measured on 2026-10-04 with the multi-thread build at the moment of a stall: the kqueue (descriptors 3, 4 and 5, one kernel object) had one queued event (`lsof` `count=1, state=0x8`) and no thread asleep on it (`lskq` kqueue status `---`, while it is `k--` with `state=0xa, count=0` in normal operation), the process used no CPU, and the runtime's driver worker was asleep in `kevent` under mio `Selector::select` for the whole `sample`. So the driver worker slept in `kevent` but not on the kqueue that held the event. `portable-pty` closes descriptors only in the forked child before `exec`. Seeing what that `kevent` waits on needs `spindump`, which runs only as root; lldb could not pause the multi-thread process. Measured on 2026-10-04 later: the PTY output is read by a blocking std thread per session (`read_output` in `vt-core/src/pty.rs`), so closing a session's PTY touches no knote of the runtime's kqueue; `a_request_after_retain_closes_pty_sessions_is_handled_at_once` passed 10 runs of 10 rounds (100 rounds) without a stall, while the stall recurred twice in the core window checks of the same day; `sudo -n` has no cached credential, so `spindump` cannot run. Retry condition: the user grants root for one `spindump` taken during a stall. Correction on 2026-10-04 at 10:2x: the kqueue, socket receive queue and `kevent` measurements above were most likely taken while the core check `a presentation that fails while the terminal service is stopped` held the service with `SIGSTOP` until the presentation failed after 10 s; the earlier traps did not exclude a stopped process. With root granted, a trap that excludes a stopped process (`ps` state `T`) recorded a `spindump` once, and it showed the service suspended (`Suspended for 201 samples`) during exactly that check. Two traps that exclude a stopped process, one on a READ knote queued for 2.5 s and one on a non-empty receive queue of the service's unix sockets for 2.5 s, did not fire during four real raster timeouts in the Wails terminal checks. So no measurement shows the service failing to read a request; the retain-related input stall is not established, and the raster timeouts of core G1.4-90-4-2 need a new diagnosis. Closed on 2026-10-04 as not a defect: the input loop reads requests at once; the refused requests after a `close` are S14.

- [o] S22 — P2: Let `PtyService::close` end a child while the reaper thread waits for it. Found on 2026-10-05 in S20: the reaper thread holds the child lock during `wait()`, so when the process-group signal fails, `close` blocks on that lock until the child exits by itself. Done on 2026-10-05: the reaper thread waits for the child's exit with `waitid(P_PID, pid, WEXITED | WNOWAIT)` without the child lock, then reaps the child and records the result under that lock and notifies a condition variable. Only the reaper thread reaps the child, so while no result is recorded the pid that `close` reads under the lock belongs to the child: `close` sends `SIGKILL` to that pid and waits for the recorded result, and an exited child stays a zombie until the reaper reaps it, so the pid is not reused before then. A failed exit wait is recorded and reported like a failed reap. Red: `close_ends_a_child_that_the_group_signal_missed_while_the_reaper_waits`, whose session has no process group and whose child ends by itself after 20 s, started `close` after the reaper thread had reached the child, and failed three times after 20.01 s with `close did not end the PTY child with SIGKILL before it returned: Some(ExitStatus(unix_wait_status(0)))`.
