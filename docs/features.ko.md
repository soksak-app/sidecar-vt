runtime의 I/O driver는 mio `Selector::select`를 거쳐 `kevent`에서 기다렸다(current-thread 빌드의 lldb 스택). 즉 이벤트는 kqueue의 활성 목록에 있었고, 기다리던 `kevent`는 그것을 돌려주지 않았다. process는 같은 knote를 나열하는 kqueue descriptor 셋(3, 4, 대기 이벤트가 하나 있었고(`lsof` `count=1, state=0x8`) 그 위에서 잠든 스레드가 없었으며(`lskq` kqueue 상태 `---`, 정상일 때는 `state=0xa, count=0`과 `k--`), process는 CPU를 쓰지 않았고, runtime의 driver worker는 `sample` 내내 mio `Selector::select` 아래 `kevent`에서 잠들어 있었다. 즉 driver worker는 `kevent`에서 잠들었지만 이벤트를 가진 kqueue에서 잠든 것은 아니다. `portable-pty`는 fork한 자식에서 `exec` 전에만 descriptor를 닫는다. 그 `kevent`가 무엇을 기다리는지 보려면 root로만 도는 `spindump`가 필요하고, lldb는 multi-thread process를 멈추지 못했다. 2026-10-04 추가 측정: PTY 출력은 session마다 blocking std thread가 읽으므로(`vt-core/src/pty.rs`의 `read_output`) session의 PTY를 닫는 일은 runtime kqueue의 knote에 닿지 사용자가 정지 중 `spindump` 한 번을 위해 root를 허락한다. 2026-10-04 10:2x 정정: 위의 kqueue, 소켓 수신 대기열, `kevent` 측정은 core check `a presentation that fails while the terminal service is stopped`가 표시가 10초 뒤 실패할 때까지 service를 `SIGSTOP`으로 멈춘 동안 찍혔을 가능성이 크다. 이전 trap은 멈춘 process를 제외하지 않았다. root를 허락받은 뒤 멈춘 process(`ps` 상태 `T`)를 제외하지 않은 trap이 `spindump`를 한 번 기록했고, 그 기록은 바로 그 check 동안 service가 정지된 상태(`Suspended for 201 samples`)였음을 보였다. 멈춘 process를 제외한 두 trap, 즉 2.5초 동안 대기열에 남은 READ knote를 보는 trap과 2.5초 동안 service unix socket의 수신 대기열이 비지 않음을 보는 trap은 Wails terminal check의 실제 raster 시간 초과 네 번 동안 한 번도 작동하지 않았다. 따라서
