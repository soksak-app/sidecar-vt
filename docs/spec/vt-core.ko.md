# 터미널 사이드카 (vt-core)

[English](vt-core.md)

터미널 사이드카(`@soksak/sidecar-vt-core`)는 [영속 서비스](https://github.com/soksak-app/core/blob/main/docs/spec/persistent-services.ko.md)이 정의한 영속 서비스의 클라이언트 모듈이다. 서비스는 애플리케이션 설정 디렉터리마다 하나의 프로세스로 실행되며 독립 PTY·셸 프로세스·VT 상태·스크롤백·IOSurface 렌더링을 소유한다. 사이드카는 터미널 세션 제어 요청을 받고 영역에 화면 그림을 공급한다.

`sidecar.json` 선언은 서비스의 process display identity를 `soksak://sidecar/vt`로 지정한다. Build는 이 선언을 읽어 executable에 embed하며, `displayName`이 없거나 유효하지 않으면 `sidecar.json`을 명시해 build를 실패한다. Service는 host 환경 변수에 의존하지 않는다. Process는 첫 start record를 쓴 뒤 runtime 초기화 전에 embedded 값을 LaunchServices에 등록한다. 등록 실패는 standard error에 보고하고 서비스 시작을 막는다. Executable path와 basename은 `build/soksak-vt-alacritty`, `soksak-vt-alacritty`로 유지한다.

파싱되지 않는 봉투는 `surface`가 문자열이면 그 표면에 `{surface, body: {error: "invalidParams", reason}}`로 답한다. 그래서 답이 보낸 표면에 닿는다. `cids`가 문자열 목록이 아니면 `reason`은 `cids must be a list of strings`이고, 그 밖이면 `Parse error: <text>`다. 읽을 수 있는 `surface`가 없는 줄은 빈 surface와 `Parse error: <text>`로 답한다.

모든 `screen` 메시지는 canonical screen hash와 replay에 사용하는 raw engine cursor `row`, `col`을 유지하고, 화면의 frame-effective caret을 위한 필수 `caret`을 포함한다. Accepted frame이 있으면 `caret`은 `{row, col}`이고, 변경된 화면의 새 frame을 기다리는 동안을 포함해 accepted frame이 없으면 `null`이다. Object는 화면 좌표이며 frame과 같은 layout에서 계산한다. Native caret 배치에는 `caret`을 사용한다. 이 값은 canonical screen hash에 포함되지 않는다. 필드 누락 또는 accepted frame의 잘못된 object는 fallback 없이 거부한다.

| 요청 | 본문 | 의미 |
| --- | --- | --- |
| `open` | `{image?: 이름}` | 영속 서비스에서 터미널 세션을 만들거나 연결하고 호스트의 그림 `configure`를 받은 뒤 영역용 그림을 할당하고 그린다. 같은 생성 식별자에 대한 `open` 호출이 여러 번이면 아무것도 하지 않는다. |
| `input` | `{actions: [InsertAction \| KeyAction \| CommandAction \| FocusAction], preedit: PreeditSnapshot}` | 하나의 순서 있는 입력 transaction을 적용한다. `actions`는 필수이며 비어 있을 수 있다. `preedit`는 필수 최종 snapshot으로, 필수 `text`, nullable `markedRange`, nullable `selectedRange`, nullable `replacementRange`, boolean `attributed`를 가진다. null range는 해당 range를 지운다. `InsertAction`은 `text`, nullable `replacementRange`, boolean `attributed`를 가진다. UTF-8 바이트는 순서대로 쓰고 range와 attribution은 native insertion metadata로 보존한다. `KeyAction`은 `key`와 boolean `shift`, `alt`, `ctrl`을 가지며 현재 terminal mode로 인코딩한다. `text`는 `key`가 `Char`일 때만 필수 문자열이고, 다른 key에서는 허용하지 않는다. `CommandAction`은 지원되는 네이티브 `selector`를 가지며 대응 key로 인코딩한다. `FocusAction`은 boolean `focused`를 가진다. focus report가 켜져 있으면 report 바이트를 해당 순서 위치에 넣는다. 서비스는 focus나 preedit 변경, 바이트 쓰기, frame 제출 전에 본문 전체와 모든 action을 검증한다. 쓰기를 만드는 모든 action을 순서대로 인코딩하고 결과 바이트가 비어 있지 않을 때 한 번 쓰며, 그 뒤 최종 preedit을 한 번 적용한다. 이미 준비된 PTY output은 최종 frame 하나를 그리기 전에 반영한다. action별 중간 frame은 제출하지 않는다. transaction의 쓰기, 준비된 output 처리, 상태 적용이 끝난 뒤에만 답한다. 앞으로 도착할 PTY echo는 기다리지 않는다. 이후 PTY read는 transaction의 최종 preedit snapshot을 유지하면서 committed screen state를 갱신한다. 잘못된 입력은 transaction 부작용이 없다. 제출한 batch write가 실패하면 오류에 실패 원인과 PTY write 진행 상태를 알 수 없다는 사실을 담으며, service는 재시도하거나 rollback을 주장하지 않는다. 기존 `bytes`, `keys`, `compose`, `focus`, `command` 본문 field는 거부한다. |
| `theme` | `{mode: "dark" \| "light", background, foreground, cursor, selection}` | 연결된 이미지 표면에 유효한 애플리케이션 외관을 적용한다. 네 색은 모두 필요한 `#rrggbb` 문자열이며 기본 배경과 전경, 커서 색, 선택 배경을 정한다. `mode`는 인덱스 ANSI 팔레트를 고른다. 세션과 셀 메트릭은 바꾸지 않는다. 다른 모드, 빠진 색, 다른 형식의 색은 `invalidParams`를 돌려주고 아무것도 바꾸지 않는다. 답은 적용한 배경을 담은 `{ack: true, event: "theme", mode, background}`다. |
| `cursor` | `{shape, blink, interval, idleTimeout, unfocused}` | 터미널 커서 정책을 적용한다. `shape`는 `block`·`underline`·`beam`, `blink`는 `Never`·`Off`·`On`·`Always`, `interval`은 양의 밀리초 정수, `idleTimeout`은 0 이상 밀리초 정수, `unfocused`는 `hollow`·`solid`·`underline`·`beam`·`unchanged`다. 잘못된 값은 `invalidParams`로 명시적으로 실패하며 대체하지 않는다. |
| `font` | `{family: string, size: number}` | `;`로 이은 우선순위 family 목록에서 터미널 글꼴을 선택하고 크기를 포인트(4–128, 글자 크기가 13 × 실제 배율로 정함)로 정한다. 서비스는 설치된 첫 family를 적용하며, 설치되어 있지 않은 family는 건너뛰고 로그에 남길 뿐 오류로 보고하지 않는다. 목록의 family가 하나도 설치되어 있지 않으면 시스템 고정폭 글꼴을 쓰고 그 사실을 로그에 남긴다. family가 하나도 없는 목록은 `{error: "invalidParams", reason, operation: "font"}`로 거부한다. 글꼴을 선택하면 셀 메트릭, 터미널 열과 행, 세션 크기, 표시 raster를 다시 계산하고, 적용한 family와 시스템 고정폭 글꼴 여부, 건너뛴 family, 크기를 담은 `{ack: true, event: "font", family, system, skipped, size}`로 답한다. 크기가 없거나 범위를 벗어나면 빈 family 목록처럼 거부한다. 첫 `font` 요청 전에는 13포인트 시스템 고정폭 글꼴을 쓴다. 앱은 글꼴을 포함하지 않으며, 터미널 페이지는 적용한 family를 `terminal.session`의 `font`와 `fontSystem`으로 보고한다. |
| `screen.read` | `{}` | 현재 화면 상태를 요청한다. 사이드카가 [영속 서비스](https://github.com/soksak-app/core/blob/main/docs/spec/persistent-services.ko.md#화면-메시지)에 정의된 `screen` 메시지의 전체 형식으로 응답하고, 페이지는 그것에서 이어 간다. 그 밖의 `screen` 메시지는 `number`를 담고 그 절의 규칙에 따라 전체 형식이나 변경 형식이다. `vt-core/src/screen_stream.rs`가 각 surface의 보낸 화면을 가진다. |
| `close` | `{}` | 터미널 세션을 종료하고 PTY를 종료한다. 호스트의 `{closed: true}` 봉투도 같은 close 동작을 사용하므로 표면을 제거해 PTY 세션을 남길 수 없다. 서비스는 세션의 프로세스 그룹을 끝낸다. 프로세스가 모두 끝났거나 끝나는 중인 그룹은(macOS가 `EPERM`으로 답한다. 읽히지 않은 출력을 남긴 셸은 터미널 출력이 비워진 뒤에야 끝난다) 이미 닫힌 것이고, 그 밖의 실패는 그룹과 남은 프로세스를 적은 오류다. |

사이드카는 frame마다 `screen` 메시지를 보내지 않고, `screen.read`에 화면의 full form으로 답한다. 이것은 [영속 서비스](https://github.com/soksak-app/core/blob/main/docs/spec/persistent-services.ko.md#화면-메시지)의 둘째 screen 형식이다. 래스터가 화면을 보이므로, 페이지는 셀이 필요할 때 읽는다. 그린 frame의 그림 봉투 뒤에, 그 frame의 커서나 scrollback이 그 image의 마지막 `view` 이벤트와 다르면 사이드카는 `{event: "view", frame, cursor, scrollback}`을 보낸다. `frame`은 그 frame의 `{generation, raster, sequence}`, `cursor`는 `caret`을 포함한 screen 메시지의 커서, `scrollback`은 `{offset, history}`다. 페이지는 이것으로 입력기 caret과 스크롤바를 둔다. 답의 `frame`은 그 화면을 보이는 frame의 `{generation, raster, sequence}`(보낸 frame의 답을 기다리는 동안 바뀐 것이 있으면 다음 frame)이거나 surface에 image가 없는 동안 null이다. 사이드카는 새 프레임이 그려질 때마다 호스트의 그림 릴레이를 통해 그림 봉투를 보낸다. 호스트 `configure`가 페이지 주도 `resize` 요청을 대체하며 최신 래스터 리비전으로 합쳐진다. 전송 그림이 `consumed`나 오류를 기다리는 동안 사이드카는 그 그림을 수정하지 않는다. 화면과 설정 변경은 대기 상태로 남고, 응답 뒤 다음 프레임이 최신 설정을 사용한다. 호스트는 region을 붙일 때와 변화마다 `{"image":{"drawing":{name, generation, drawing}}}`를 보낸다([drawing](https://github.com/soksak-app/core/blob/main/docs/spec/native-surfaces.ko.md#그림-영역)). surface는 첫 상태가 올 때까지 그린다. region이 그리지 않는 동안 surface는 frame을 그리지 않고 그림 봉투를 보내지 않으며, 출력을 engine에 적용하고 `screen.read`에 답한다. region이 다시 그리면 바뀐 화면을 한 번 그리며, 보낸 frame이 있으면 그 답 뒤에 그린다. 마지막으로 적용한 상태나 설정된 그림보다 이전 generation의 상태는 무시하고, 이 message에는 답이 없다. 문자열 `name`, 숫자 `generation`, boolean `drawing`이 없는 message에는 `invalidParams`로 답한다.

`screen.read`의 각 답은 `render`를 가진다. 서비스가 기존 시작 옵션 `SOKSAK_VT_TRACE_DIR`을 지정해 시작한 diagnostic build가 아니면 이 값은 null이다. 대응하는 프레임을 그리지 않은 경우에도 null이다. 활성화되면 메시지가 지정한 정확한 `frame`의 metadata이며 frame identity를 반복한다. Pixel width, height, byte stride, `bgra8` 형식, premultiplied alpha, `sRGB` 색 공간, top-left pixel 원점, grid 행·열과 원점, device-pixel 셀 너비·높이, 실제 CoreText 글꼴 크기·ascent·descent·leading, baseline과 underline geometry, cursor 사각형·모양·표시·focus·blink 표시 상태·blend mode와 해당 blend가 색을 사용하는 경우의 effective color, 해당 프레임에서 그린 비어 있지 않은 각 grapheme의 ink bounds를 담는다. Glyph bounds는 grapheme을 그린 CoreText glyph 또는 line run에서 얻는다. 각 glyph는 line fallback 경로를 포함해 실제 draw에 사용한 CoreText font run 수를 양의 정수로 보고한다. Glyph와 underline 사각형은 fractional top-left cell-local pixel 좌표를 사용한다. 각 glyph는 grid 안에 보이는 cell span을 `width`로 보고하고, cell default와 inverse video를 적용한 뒤 실제 draw가 사용한 effective `foreground`, `background`를 불투명한 `#rrggbb` sRGB 색으로 제공한다. Preedit overlay도 동일하다. Overlay가 덮은 원래 PTY cell과 screen 메시지의 `screen.cells`는 그대로이므로 consumer는 overlay 색을 원래 cell에서 추론하지 않는다. Underline 색은 해당 glyph의 effective `foreground`다. Difference blend를 사용하는 block cursor는 destination pixel을 반전하므로 configured cursor color를 사용하지 않으며 `color: null`을 보낸다. Renderer는 draw 입력과 geometry만 보고하며 pixel threshold나 coverage 판정은 포함하지 않는다. 기본 경로는 glyph bounds를 계산하거나 셀별 render 기록을 할당하지 않는다. Frame과 render metadata는 같은 성공 draw에서 함께 만들어 image 메시지를 보내기 전에 고정한다. 실패하거나 지연된 draw에는 대기 중인 화면 상태의 render metadata가 없다.

Host는 terminal session을 닫지 않고 native image owner를 해제하기 위해 `body.image.detach: {request, name, generation}`을 `body.image`의 유일한 action으로 보낸다. `request`는 비어 있지 않은 opaque string이고 `generation`은 양의 JavaScript-safe integer다. 필드 누락, 잘못된 type, 추가 action은 `invalidParams`로 답하고 상태를 바꾸지 않는다. `request`가 비어 있지 않은 string이면 이 답은 받은 `request`, `name`, `generation`과 `ok: false`, `error: "invalidParams"`, `reason`을 담은 `body.image.detached`다. Attachment가 stale이어서 거부된 detach는 `error: "stale attachment"`로 같은 형식으로 답한다. 비어 있지 않은 string `request`가 없는 detach는 `{error, reason}` 오류 봉투로만 답한다. Sidecar는 같은 `request`, `name`, `generation`을 포함하고 `{ok: true, result: "detached" | "alreadyDetached" | "alreadyAbsent"}` 또는 `{ok: false, error, currentGeneration?}`를 포함한 `body.image.detached`로 답한다. Host는 세 값을 모두 확인하고 supplier와 surface까지 일치시켜 응답을 연결한다. Owner마다 detach 하나만 outstanding 상태로 허용하며 acknowledgement 뒤에 다음 open 또는 image configuration을 보낸다. 최신 request identifier를 다른 surface, name 또는 generation과 함께 재사용하면 `error: "requestMismatch"`로 거부하고 이전 결과를 다른 tuple에 재사용하지 않는다.

설정된 image의 name과 generation이 정확히 맞으면 sidecar는 해당 generation의 image 상태, 대기 중 configuration, 요청 image를 제거하고 surface를 headless mode로 바꾼 뒤 `ok: true, result: "detached"`로 답한다. Terminal engine, session, PTY, process, input state와 history는 유지한다. Name이 요청되었지만 아직 configuration이 generation을 전달하지 않았다면 인증된 host가 보낸 양의 generation을 제한된 최신 분리 generation으로 기록하고 요청을 지운 뒤 `detached`로 답한다. 설정·요청·대기 중인 image가 모두 없으면 `alreadyAbsent`로 답한다. 최신 분리 name과 generation에 대한 반복 detach는 더 새로운 generation이 설정 또는 요청되지 않은 동안 `alreadyDetached`로 답한다. 더 새로운 generation을 알게 된 뒤 이전 generation을 detach하면 `error: "staleGeneration"`으로 거부한다. 알려진 attachment보다 높은 generation은 `error: "futureGeneration"`으로 거부한다. Name이 다르면 `error: "imageNameMismatch"`로 거부한다. 알려진 경우 오류에는 `currentGeneration`을 포함하며 현재 attachment는 바꾸지 않는다. 같은 request를 재전송한 경우에도 owner 상태가 유지되는 동안만 idempotent하게 처리한다. Persistent session을 reconnect해도 새 image owner가 생기지 않으므로 최신 detach request의 replay를 유지한다. 이후 image가 있는 open 또는 configuration은 새 owner를 만들며 기존 replay를 stale로 만든다. Request 재생 상태는 최신 request와 분리 generation만 보관해 제한한다.

Acknowledgement는 render attachment, 대기 중 configuration, 요청 image가 분리되었음을 뜻한다. 이미 보낸 image transfer는 기존 수명 규칙에 따라 정확히 일치하는 `consumed` 또는 오류 응답을 받거나 연결이 끝날 때까지 불변으로 보존한다. Detach는 해당 lease를 해제하거나 옮기지 않는다. Image 응답은 name, generation, raster, sequence 전체가 일치해야 하므로 분리된 image의 늦은 응답이 새 generation의 pending draw를 해제할 수 없다. Acknowledgement 뒤 image 없는 `open`은 허용되며 기존 session을 재사용한다. 이후 image가 있는 `open`과 `configure`는 같은 session에 새 generation을 연결할 수 있다. `close`는 계속 PTY를 닫으며 image detach 용도로 쓰지 않는다. Message envelope는 protocol 1을 유지하고 저장 형식은 바꾸지 않는다.

Rust interface `protocol::screen_line(surface, body)`는 소유한 정규화 screen body를 소비하고 compact JSON surface envelope를 반환한다. Raster 및 headless screen sender는 같은 encoder를 사용한다. Screen 검증과 정규화는 encoding 전에 수행하며 encoder는 모든 body 값을 보존하고 cell tree를 다시 만들지 않으며 직렬화 오류를 기존 screen-error 경로로 반환한다.


## Event writer

Service는 공통 event-log contract를 따른다. 100 ms batch interval은 이전 flush부터 pending batch의 대기 시간을 제한하며 다른 이벤트를 받아도 deadline을 다시 시작하지 않는다. Error 및 명시적 flush 요청은 pending 기록을 즉시 쓴다.

## 영속 터미널 서비스

아래 절은 이 저장소가 가진 터미널 서비스 계약이다. 서비스 자체는 [영속 서비스](https://github.com/soksak-app/core/blob/main/docs/spec/persistent-services.ko.md)가 정의하며, 이 절들이 이름만 드는 다른 core 명세는 이름으로만 가리킨다.

### 터미널 세션 시작

세션은 터미널 설정 `terminal.shell`이 이름 붙인 셸을 시작한다. 기본값 `login`은 계정의 사용자 데이터베이스 항목의 로그인 셸이며, 다른 값은 실행 가능한 파일의 절대 경로여야 한다. 셸은 로그인 셸로 시작한다. `argv[0]`은 `-`와 파일 이름이고 `SHELL`은 그 경로다. 터미널 페이지는 값을 `open` 요청의 `shell`로 보내고, workbench는 백그라운드 세션에 대해 플러그인의 `background.settings`를 통해 보낸다. 값이 없거나, 상대 경로이거나, 파일이 없거나 실행할 수 없거나, 계정에 로그인 셸이 없으면 명시적 오류이며, 그 대신 다른 셸을 시작하지 않는다. 설정을 바꾸면 그 뒤에 열리는 세션부터 적용된다.

터미널의 문자 인코딩은 UTF-8이다. 셸은 터미널 서비스의 환경을 받는다. 그 환경에서 `LANG`, `LC_ALL`, `LC_CTYPE`가 모두 없거나 비어 있으면, 서비스는 현재 macOS 로캘의 언어와 지역 코드로 `LANG`을 `<language>_<region>.UTF-8`로 정한다. 그 로캘이 설치되어 있지 않거나 macOS 로캘에 언어나 지역 코드가 없으면, 서비스는 대신 `LC_CTYPE=UTF-8`을 정하고 서비스 로그에 `terminal: locale <name> is not installed; LC_CTYPE=UTF-8`을 쓴다. 비어 있지 않은 `LANG`, `LC_ALL`, `LC_CTYPE`은 그대로 둔다. Finder나 Dock에서 시작한 애플리케이션은 세 변수를 하나도 받지 않으므로, 이 규칙이 없으면 셸은 C 로캘에서 실행되어 ASCII가 아닌 문자의 바이트를 따로 센 문자로 보고 이스케이프 수열로 보여 준다. 실행 중인 터미널 서비스는 세션이 끝날 때까지 시작할 때의 환경과 실행 파일을 유지한다.

`open` 요청은 `directory`를 담을 수 있다. 셸은 이 디렉터리에서 시작하며, 존재하는 디렉터리의 절대 경로가 아닌 값은 명시적 오류이고 다른 디렉터리를 대신 쓰지 않는다. 없으면 셸은 계정의 홈 디렉터리에서 시작한다. 터미널 페이지는 표면의 `origin.directory`(호스트 플러그인 계약의 탭 보고)가 `null`이 아니면 그것을 보낸다. 따라서 터미널에서 나뉜 터미널은 앞 터미널이 마지막으로 보고한 디렉터리에서 시작한다. 그렇지 않으면 표면 맥락의 `project.root`를 보내므로, 프로젝트의 새 터미널은 프로젝트 루트에서 시작한다. 프로젝트가 없는 창에서는 `directory`를 보내지 않는다.

사이드카는 OSC 133 표시를 보고하는 셸 통합을 zsh와 bash에 적용하며, 사용자의 파일은 바꾸지 않는다. 통합 스크립트는 사이드카에 담겨 있고, 세션이 시작하기 전에 `<임시 디렉터리>/soksak-shell-<내용 해시>/`(모드 0700)에 쓰인다. zsh의 경우 사이드카는 `ZDOTDIR`을 그 디렉터리로 정하고 기존 `ZDOTDIR`은 `SOKSAK_ZSH_ZDOTDIR`에 보관한다. 그 디렉터리의 `.zshenv`는 원래 `ZDOTDIR`을 되돌리고, 사용자의 `.zshenv`를 `source`하며, 대화형 셸에 hook을 설치한다. zsh는 나머지 시작 파일을 되돌린 디렉터리에서 읽는다. bash의 경우 사이드카는 `SOKSAK_BASH_INTEGRATION`에 스크립트 경로를 담아 내보내고, `PROMPT_COMMAND`의 첫 항목은 현재 `DEBUG` trap을 기록한 뒤 스크립트를 `source`한다. bash 3.2에서는 `source`로 읽은 파일이 `DEBUG` trap을 보지 못하기 때문이다. 이 항목 뒤에는 구분자가 없으므로 시작 파일이 `;`로 항목을 앞이나 뒤에 더할 수 있다. 셸은 시작 파일을 바꾸지 않고 읽는다. 첫 프롬프트에서 스크립트는 `PROMPT_COMMAND`에서 자기 항목을 지우고(다른 항목 사이에 있으면 `:`가 된다), 두 변수의 내보내기를 멈추며, 자기 hook을 사용자 항목의 앞과 뒤에 둔다. 사이드카는 bash를 `ENV`를 쓰는 POSIX 모드로 시작하지 않는다. bash 3.2는 `sh`로 실행될 때만 `ENV`를 읽는데, 셸은 `argv[0]`이 `-bash`인 로그인 셸로 남아야 하기 때문이다. 사용자의 시작 파일이 `PROMPT_COMMAND`를 바꾸면 스크립트는 한 번도 실행되지 않으며, 세션은 통합이 없는 셸처럼 동작한다. 다른 셸은 통합 없이 시작한다.

hook은 프롬프트 앞마다 `133;A`를 보고하고(bash는 readline이 프롬프트의 마지막 줄만 다시 그리므로 `133;A;redraw=last`를 보고한다), 명령이 실행되기 전 `133;C`를, 다음 프롬프트 앞 `133;D;<status>`를 보고한다. 프롬프트 앞마다 작업 디렉터리도 `7;file://<호스트 이름><경로>`로 보고하며, 경로는 비예약 문자와 `/`를 뺀 나머지를 퍼센트 인코딩한다. zsh는 `preexec` hook에서 `C`를 보고한다. bash 3.2에는 그런 hook이 없으므로 `DEBUG` trap이 프롬프트 뒤 첫 명령에서 `C`를 보고한다. 첫 `PROMPT_COMMAND` 항목이 그 대기를 취소한다. 빈 입력 줄은 명령 없이 `PROMPT_COMMAND`를 실행하기 때문이다. 스크립트가 자기를 설치하는 프롬프트에서는 자기 실행 뒤의 항목이 trap이 생긴 뒤에 실행되므로, 텍스트가 그 항목 중 하나와 같은 명령은 그 프롬프트에서 보고되지 않는다. trap은 마지막 인자로 `$_`를 넘기므로 다음 명령을 위해 `$_`가 유지된다. 시작 파일이 `DEBUG` trap을 설정했으면 스크립트는 그것을 바꾸지 않고 표시를 보고하지 않는다. `C` 없는 `A`는 크기 조정 때 명령 출력을 지우기 때문이다.

### 터미널 서비스 구현

영속 터미널 서비스 하나가 애플리케이션 설정 디렉터리 하나의 PTY, VT 상태, 스크롤백, 렌더링을 소유한다. PTY 관리, 에뮬레이션, 렌더링, 클라이언트 전송은 그 프로세스 안의 별도 모듈이며 별도 실행 파일이 아니다. 독립된 세션은 각자의 PTY 장치와 셸 프로세스를 소유한다. PTY 장치는 프로세스가 아니다. 독립된 터미널 셋에는 애플리케이션 호스트 외에 서비스 하나와 셸 셋이 필요하다. WebKit 프로세스와 셸이 실행한 프로그램은 따로 센다.

서비스는 엔드포인트를 게시하기 전에 기본 터미널 글꼴을 읽는다. 그래서 서비스 프로세스의 첫 CoreText 호출이 그 프로세스의 첫 터미널만 지연시키고 이후 터미널은 지연시키지 않는다. 이 비용은 서비스 프로세스마다 한 번만 생기고 서비스는 애플리케이션 재시작보다 오래 살기 때문에 받아들인다.

터미널 사이드카는 종료 이유를 `sidecar.vt.session_stop` 이벤트에 적는다. 이유는 `folder-removed`, `endpoint-removed`, `endpoint-replaced`다.

터미널 페이지는 이것을 재연결 신호로 쓴다. 페이지는 오래된 사이드카 오류를 해결하고, 입력이 다시 대기열에 들어가도록 세션 게이트를 닫으며, 세션 부트스트랩을 다시 실행한다. 부트스트랩은 `open`(보존된 세션에서는 아무것도 하지 않고, 새 서비스에서는 새 세션을 만든다)에 이어 마지막 테마, 선언된 글꼴, 커서 정책을 보낸다.

### PTY 출력과 입력

세션 하나에 I/O task가 하나 있다. task는 PTY master의 non-blocking 복제본을 `tokio::io::unix::AsyncFd`로 소유하고, 세션은 resize와 `FIONREAD` 측정을 위해 `portable-pty`의 master를 유지한다. 이 경로는 `Engine::feed(&[u8])` 앞에 있어 모든 엔진이 쓴다. 터미널 라이브러리의 event loop와 `tty` module은 쓰지 않는다. 그 handler는 한 엔진에 타입이 고정되어 있고, 그 프로세스 시작과 resize는 이 명세의 세션 시작과 충돌하기 때문이다.

**출력.** task는 한 번에 최대 64 KiB를 읽고, 세션의 16 chunk 출력 channel의 permit을 쥔 동안에만 읽는다. 그래서 세션은 엔진이 소비하지 않은 출력을 최대 1 MiB까지 쥔다. channel이 차면 읽기만 멈춘다. 그러면 프로그램은 자기 write에서 기다리고 출력은 버려지지 않는다. 지난 출력의 ring과 attach replay는 없다. surface 하나가 세션 하나를 소비하고, persistent service는 바이트가 아니라 세션 상태를 복원한다.

**입력.** write는 task의 FIFO queue 하나를 지나고, surface task 안에서 기다리지 않는다. 어떤 바이트도 앞선 바이트를 앞지르지 않는다. 키와 붙여넣기는 queue의 바이트와 새 바이트의 합이 64 MiB를 넘으면 명시적 오류로 거부된다. 이 상한은 사람이 붙여넣는 양보다 훨씬 큰 붙여넣기를 통과시키고, 멈춘 세션이 쥐는 양을 제한한다. 엔진이 프로그램에 보내는 응답은 거부되지 않는다. 거부된 응답은 프로그램을 계속 기다리게 하기 때문이다. queue의 바이트가 상한을 넘은 동안 task는 출력 읽기를 멈추므로 프로그램은 응답을 더 일으키지 않고, service는 읽기가 멈출 때와 다시 시작할 때 `{event: "input_held", queued, held}`와 기록 `sidecar.vt.input_held`를 보고한다. interrupt 바이트도 이 순서를 지키므로 앞선 입력 뒤에야 프로그램에 닿는다. 읽기가 멈춘 동안에는 터미널 출력이 비기를 기다리는 프로그램과 그 프로그램을 기다리는 queue가 움직이지 않는다. 메모리는 제한되고, event가 상태를 보이고, close가 세션을 끝낸다. 상한을 넘는 엔진 응답만 이 상태에 이르며, 이는 응답을 읽지 않고 계속 일으키는 프로그램에서 생긴다.

**write 결과.** task는 각 write의 결과를 순서 있는 stream 하나로 보고하고, surface는 그 stream에서 acknowledgement와 `sidecar.vt.pty_write` 기록을 보낸다. `ok: true`는 master가 모든 바이트를 받았다는 뜻이다. 완성된 줄이 없는 canonical tty는 바이트를 받고 버릴 수 있으므로, `ok: true`는 프로그램이 읽었다는 뜻이 아니다. `ok: false`는 실패 지점 뒤의 바이트를 프로그램이 받지 못했다는 뜻이고, 기록에 이유가 실린다.

**child 종료.** child가 reap되면 task는 read가 0을 돌려주거나 대기해야 할 때까지, 또는 64 KiB를 더 읽을 때까지 읽는다. queue에 있거나 일부만 쓰인 입력을 각각 `ok: false`와 이유 `child exited`로 끝내고, master descriptor 둘을 닫은 다음, chunk와 `Exit`를 출력 channel로 보낸다. 그 뒤 남은 job이 쓰는 바이트는 다른 session의 job에서도 그 job에서 오류로 실패하거나 hangup으로 그 job을 끝낸다. service는 그 바이트를 읽지 않았고 쥐지 않는다. macOS에서는 session leader의 종료가 master가 열려 있어도 이미 그 write를 실패시키고, master를 닫으면 terminal이 풀린다. reaper가 보고하기 전에 master write가 EIO로 실패하면 queue는 그 보고나 close를 기다린다. child 종료는 아무것도 kill하지 않는다. 세션 항목은 명시적 close나 owner close까지 남는다. `Exit` 뒤 write는 `session writer is closed`를, resize와 측정은 `session master is closed`를 돌려준다. `Exit` 뒤 첫 close는 process group을 kill하고 `sidecar.vt.kill`로 기록하고 항목을 지운다. surface는 `Exit`로 끝나기 전에 frame clock이 쥔 화면을 그린다.

**close.**

| close 시점의 상태 | 결과 |
| --- | --- |
| queue에 있거나 일부만 쓰인 입력 | `ok: false`와 이유 `session closed`로 끝난다 |
| 출력 channel의 예약된 permit | 반납된다 |
| 읽었고 아직 보내지 않은 chunk | permit이 있으면 보낸다. 없으면 바이트 수와 함께 `sidecar.vt.buffer_dropped`로 기록한다 |
| close와 reap이 동시에 일어남 | close가 결정하고 `Exit`가 한 번 뒤따른다 |
| 두 번째 close | 첫 close의 idempotent 결과를 돌려준다 |
| close가 프로그램에 쓰는 바이트 | 없다 |
| master | child를 기다리기 전에 두 descriptor를 닫는다. 읽히지 않은 터미널 출력이 있는 프로세스는 그 출력이 비거나 master가 닫혀야 끝나기 때문이다 |
| child와 job | child에 SIGHUP을 보내 shell이 job에 전하게 한다. reaper를 최대 250 ms 기다린다. 그다음 남은 child와 process group에 SIGKILL을 보낸다. `nohup`이나 `disown`으로 시작한 job은 계속 돈다 |

이 결정은 터미널 구현의 보편적 형태를 따른다. 출력은 무손실이고, reader는 상한에서 멈추고, 쓰기는 읽기와 분리된다. 답한 이의는 다음과 같다.

- 기각: control byte가 queue를 앞지른다. 프로그램이 순서대로 읽는 바이트 stream의 순서를 바꾸며, 읽지 않는 프로그램에 interrupt가 닿는지는 kernel line discipline이 정하고 tracked test가 밝힌다.
- 기각: 최신 화면만 쥐는 client task. 출력을 버리거나 엔진 밖에 화면 상태가 필요하다.
- 기각: 이 변경에 engine thread를 넣는다. 지금 엔진은 모두 `Send`다. `Send`가 아닌 엔진은 surface task를 current-thread runtime과 `LocalSet`의 자기 thread에서 돌린다. channel은 이미 thread를 건너므로 호출부가 바뀌지 않는다.
- 기각: 상한에서 command channel을 멈춘다. 그 channel은 close와 resize도 실으므로 멈춘 프로그램이 이들까지 멈춘다.
- 기각: child 종료 때 세션의 모든 프로세스를 kill한다. 자기 group의 job은 터미널이 닫힌 어떤 터미널에서처럼 터미널 없이 계속 돈다.
- 기각: child 종료 때 64 KiB 상한 뒤의 바이트를 센다. 읽지 않았으므로 셀 값이 없고, 그 바이트를 쓰는 쪽이 오류를 받는다.
- 수용: child 종료 때 master를 닫고 hangup을 test한다. `Exit` 뒤 첫 close가 kill하고 기록한다. `Exit` 때 쥔 화면을 그린다. 읽기가 멈추면 event를 보낸다. `AsyncFd`는 자기 descriptor를 소유하고 세션은 resize에 master가 필요하므로 복제 descriptor를 `AsyncFd`에 둔다.

### 터미널 입력과 표시

#### 네이티브 명령 action

`CommandAction`은 선언된 terminal key 매핑이 있는 selector만 지원한다: `insertNewline:`은 Enter, `deleteBackward:`는 Backspace, `deleteForward:`는 Delete, `cancelOperation:`은 Escape로 매핑한다. Sidecar는 각 명령을 ordered input transaction의 해당 위치에서 이 key로 인코딩한다. `cancelOperation:`은 Escape 바이트 하나(`0x1b`)를 만들며 producer는 원본 Escape key를 다시 보내지 않는다. Native input producer는 AppKit의 `noop:`을 로컬에서 처리하므로 transaction으로 보내지 않는다. 다른 selector는 PTY write, preedit 변경 또는 frame 제출 전에 명시적인 `invalidParams` 오류가 된다.

터미널을 한 번 포인터로 누르면 선언된 `terminal.focus` 명령을 통해 키보드 소유권이 그 네이티브 그림 영역으로 넘어간다. 호스트는 네이티브 터미널 입력 뒤에 오는 합성 포인터를 전달하기 전에 대상 문서 WebView를 응답자로 되돌리므로, 네이티브 그림 응답자가 다음 클릭을 막을 수 없다. DOM 앵커는 포인터의 기본 DOM 포커스 동작을 막아, 같은 클릭 동안 WebKit이 소유권을 되돌리지 못하게 한다. 카드 선택은 여전히 그 이벤트를 받는다. 두 번째 클릭, 지연된 재포커스, 테스트 전용 포커스 명령은 필요하지 않다. 포커스 요청 오류는 계속 관찰할 수 있다. 모달 포커스 복원과 그림 포커스 알림은 활성 AppKit/Tauri 콜백 뒤로 미룬다. 그것들이 WebView 이벤트 경로에 동기적으로 다시 들어가면 안 된다.

엔진, PTY, 표시된 래스터는 적용된 크기에 대해 일치한다. 좁히면 소프트 줄바꿈된 주 화면의 줄이 다시 배치되고, 넓히면 같은 논리 줄이 다시 이어진다. 좁히는 재배치가 더하는 행은 먼저 커서 아래의 빈 행을 쓴다. 위의 행은 화면에 남고, 들어가지 못한 행만 기록으로 옮겨진다. 그래서 나중에 행을 늘려도 그 행이 프롬프트 위로 돌아오지 않는다. 명시적 줄바꿈은 그대로 남는다. 대체 화면 응용 프로그램은 터미널이 정한 배치 의미를 유지한다. 구분선 이동은 글꼴 메트릭을 바꾸지 않으며 래스터 기하를 애니메이션하지 않는다. 셀 하나를 담을 공간이 없는 래스터는 구성 중의 일시 상태이며 잘못된 요청이 아니다. 사이드카는 현재 격자를 유지하고 래스터를 받아들여 프레임을 보인다. 그림은 래스터에 잘리므로 셀보다 작은 래스터는 들어가는 부분만 보인다. PTY는 크기를 유지하므로 자식 프로세스는 창 변화를 보지 못한다. 래스터에 셀 하나를 담을 공간이 없는 동안 열린 표면은, 그 공간이 맞는 래스터가 올 때까지 닫힌 상태로 남는다. 두 경우 모두 오류를 보고하지 않는다.

엔진은 OSC 133 표시에서 셸 상태를 얻는다. `A`와 `B`는 표시의 `redraw` 매개변수(없으면 `1`, `0` 또는 `last`, 다른 값은 거부)로 프롬프트 상태를 정하고, `C`와 `D`는 출력 상태를 정한다. `A`는 커서가 0열이 아니면 먼저 커서를 다음 줄의 시작으로 옮기고, 그 행을 프롬프트 시작으로 기록한다. 프롬프트 상태의 ED 2는 프롬프트 시작을 맨 위 행으로 옮긴다. 셸이 새 표시 없이 거기서 프롬프트를 다시 그리기 때문이다. 다시 그리기 영역은 `redraw=1`이면 프롬프트 시작에서, `redraw=last`이면 커서 논리 줄의 첫 행에서 시작한다. 주 화면이 프롬프트 상태에서 `redraw`가 `0`이 아닌 채로 크기가 바뀌면, 엔진은 재배치하고 다시 그리기 영역의 첫 행부터 화면 아래까지의 행을 지운다. 그리고 재배치 전에 커서가 그 첫 행 아래 있던 행 수만큼 아래에 있는 행의 0열로 커서를 옮긴다. 그 행이 맨 아래보다 아래이면 화면을 위로 스크롤한다. 재배치는 논리 줄을 유지하므로, 엔진은 첫 행을 그 행과 커서 사이의 논리 줄 수로 다시 찾는다. zsh는 `SIGWINCH` 뒤에 프롬프트 전체를 다시 그리고, bash(readline)는 프롬프트의 마지막 줄만 다시 그린다. 둘 다 마지막으로 그린 너비에서의 커서 행 수만큼 위로 올라가므로 영역의 첫 행부터 다시 시작하며, 지워진 행은 이전 너비의 행을 남기지 않는다. 그래서 자기 줄 끝까지 차는 프롬프트(두 줄 프롬프트나 마지막 행을 채운 프롬프트)도 위의 출력을 지키지 않는다. 스크롤백이 가장 오래된 행을 버린 뒤에도 프롬프트 시작은 맞다. 가장 오래된 기록 행과 커서 사이에 있지 않게 되면, 엔진은 오류를 보고하고 아무것도 지우지 않는다. 셸이 다시 그리기 전에 크기가 또 바뀌면, 셸은 이미 현재가 아닌 너비로 그려서 프롬프트 위의 행을 덮어쓸 수 있다. 현재 크기와 같은 크기로의 변경은 아무것도 바꾸지 않는다. PTY는 그런 경우 `SIGWINCH`를 보내지 않기 때문이다. 통합이 없는 셸은 표시를 보내지 않으며, 크기 변경 뒤 셸 자신의 다시 그리기는 이전 너비의 행을 남길 수 있다.

화면 지우기 2(`ESC[2J`)는 화면의 모든 셀을 현재 배경으로 지우고 기록과 커서는 그대로 둔다. 그래서 기록(`ESC[3J`)을 지운 뒤 화면을 지우는 `clear`는 되돌아갈 기록도 스크롤바도 남기지 않는다. 화면 지우기 1(`ESC[1J`)은 커서 위의 모든 줄과 커서 줄의 커서 셀까지를 지운다. 엔진은 두 동작을 격자 라이브러리에 넘기지 않고 출력의 그 위치에서 직접 적용한다. 라이브러리는 `ESC[2J`에서 보이는 줄을 기록으로 옮기고, 커서가 둘째 줄에 있을 때 `ESC[1J`에서 첫 줄을 남기기 때문이다.

사이드카는 호스트가 앞의 래스터에 `consumed`로 답한 뒤에만 래스터를 그린다. 호스트가 래스터를 들고 있는 동안 화면을 바꾸는 출력, 스크롤, 입력은 그 화면을 바뀐 것으로 표시만 하고 그리지 않는다. 호스트가 답하면 사이드카는 [frame clock](#frame-clock)에 맞춰 현재 화면을 한 번 그린다. 그래서 출력이 많이 쏟아져도 출력 조각마다가 아니라 호스트의 답마다, 그리고 clock 구간마다 많아야 래스터 하나가 생긴다. `screen` 답의 구성원은 [화면 메시지](https://github.com/soksak-app/core/blob/main/docs/spec/persistent-services.ko.md#화면-메시지)에 정의되어 있다.

터미널 래스터는 실제로 적용된 애플리케이션 외관을 따른다. 표면 페이지는 사이드카가 시작할 때와 애플리케이션 테마나 모드가 바뀔 때마다 `theme`을 보낸다. 내용은 `mode`(`dark` 또는 `light`)와, 페이지가 받은 테마 토큰에서 얻은 네 색이다. `background`는 `--card`이고, `foreground`와 `cursor`는 `--fg`다. 터미널이 채우는 카드의 색이므로, 터미널은 애플리케이션의 다른 모든 표면처럼 카드의 일부로 보인다. `selection`은 `--rail`, 즉 테마의 강조 레일이므로 선택된 텍스트가 카드와 테두리와 뚜렷이 구분된다. 테마에는 표면 색이 따로 없다. 셸 페이지, 터미널, 네이티브 표면이 그리기 전에 보이는 대역 모두 `--card`와 `--fg`를 쓰므로, 어떤 표면도 애플리케이션의 다른 곳이 쓰지 않는 색을 보이지 않는다. 사이드카는 다른 모드와 `#rrggbb`가 아닌 색을 거부한다. 색은 기본 배경과 전경, 커서, 선택 배경을 바꾼다. 선택된 셀은 프로그램이 OSC 17이나 19 강조 색을 정하지 않는 한 그 배경 위에서 자기 텍스트 색을 유지한다. `mode`는 인덱스 ANSI 팔레트를 고르며, 테마는 그 팔레트를 바꾸지 않는다. 프로그램이 표준 팔레트와의 대비에 맞춰 그 색을 고르기 때문이다. 페이지는 적용된 모드와 배경을 `terminal.session`의 `theme`과 `background`로 보고한다. 래스터는 셀 격자 밖의 그림, 즉 마지막 열의 오른쪽과 마지막 행 아래를 현재 기본 배경으로 채운다. 기본 배경은 테마 배경이거나, 프로그램이 OSC 11로 정한 색이다. 화면은 그 색을 `background`로 보고한다. 이 변경은 이후와 기존 화면 셀에 적용되며, PTY, 세션, 텍스트, 커서 위치, 셀 메트릭을 다시 만들지 않는다. 모드는 그림 표면의 속성이며 다음 완전한 프레임에 적용된다. 전송 중인 그림은 바뀌지 않는다.

터미널 탭은 프로그램 제목을 보인다. 페이지는 OSC 0이나 OSC 2 제목을 `tab.title`로 보고하고, 제목 재설정에서 그것을 지운다. 터미널 설정 `terminal.title`은 `program`(기본값) 또는 `name`을 고른다. `name`이면 페이지는 제목을 보고하지 않고 보이는 제목을 지운다. `program`으로 되돌리면 프로그램이 마지막으로 정한 제목이 보인다. `tab.title`이 거부하는 제목은 세션 오류다. OSC 8 하이퍼링크 안의 셀은 화면에서 자기 URI를 `link`로 가지며, 래스터는 SGR 4 텍스트처럼 밑줄을 긋는다. 링크 셀 위의 포인터는 손 모양이다. 링크 셀에서 Command-클릭하면 그 URI를 담아 선언된 `terminal.link.open` 명령을 실행하며, 이 명령은 `runtime.links.open`(호스트 플러그인 계약의 링크 열기)으로 링크를 연다. 클릭은 선택을 시작하지 않는다. Command 없는 클릭은 선택 동작을 그대로 둔다. 호스트가 거부하는 URI는 입력 세션 오류다. 페이지는 OSC 9 알림마다 `terminal.notifications` 정책(기본값 `tab`, 또는 `system`)에 따라 `tab.notify`에 넘긴다. 그것이 거부하는 알림은 세션 오류다. `tab` 정책은 탭 알림을 보인다. `system` 정책은 호스트 알림 센터에만 보내며, 호스트가 제공할 수 없으면 네이티브 오류가 관찰 가능한 채로 남고 페이지는 대체 경로를 쓰지 않는다. 페이지는 OSC 7 이벤트의 디렉터리를 `tab.directory`로 기록한다. 사이드카의 `directory` 이벤트는 URI와 `path`를 담는다. `path`는 스킴이 `file`이나 `kitty-shell-cwd`이고 호스트가 비었거나 `localhost`이거나 로컬 호스트 이름이면 퍼센트 디코딩한 절대 경로이며, 다른 기기의 디렉터리이면 `null`이고 기록된 디렉터리를 지운다. 다른 스킴의 URI, 상대 경로, 디코딩할 수 없는 경로는 엔진 오류로 거부한다.

커서 상태는 위치, 가시성, 모양, 깜박임 정책, 색을 포함한다. 커서 정책은 명시적이다. 모양은 `block`, `underline`, `beam` 중 하나다. 깜박임은 `Never`, `Off`, `On`, `Always` 중 하나다. 간격은 양의 밀리초 값이다(기본값 750). 유휴 시간 제한은 0 이상의 밀리초 값이다(기본값 5000, 0이면 제한을 끈다). 포커스를 잃었을 때의 렌더링은 `hollow`, `solid`, `underline`, `beam`, `unchanged` 중 하나다. 기본값은 포커스가 있을 때 `Off` 깜박임의 채워진 블록이고, 포커스가 없을 때 고정된 속이 빈 블록이다. `Never`와 `Always`는 프로그램의 깜박임 요청을 재정의하고, `Off`와 `On`은 그것을 허용한다. 프로그램의 커서 모양은 설정된 기본값을 재정의한다. 프로그램의 가시성이 우선한다. 터미널 모듈은 사이드카가 `cursor` 동작에 답한 뒤 `terminal.cursor`에 정책을 보고한다. 모듈은 그 정책으로 그린 프레임을 표시한 뒤에 `cursor`를 보낸다. `terminal.cursor`는 `drawn`도 보고한다. `drawn`은 프로그램의 요청과 포커스 규칙을 거쳐 사이드카가 그린 모양(`block`, `underline`, `beam`, `hollowBlock`, `hidden` 중 하나)과 깜박임 요청이다. 사이드카가 표시하는 모든 래스터는 그 화면의 `screen` 이벤트를 함께 가지므로, 포커스 변경이나 다른 다시 그리기는 위치, 포커스, `drawn`을 픽셀과 함께 갱신한다. 렌더링은 커서 픽셀만 바꾼다. 페이드나 크기 애니메이션은 없으며, PTY를 다시 만들거나 셀 메트릭을 바꾸지 않는다. 커서는 그 위치 문자의 표시 너비를 덮는다. 이때 그 위치에 보이는 조합 전 텍스트도 포함한다. 넓은 문자는 두 셀 커서로 덮이며, 커서는 마지막 열을 넘지 않는다. 조합 전 텍스트 중에는 제공된 `selectedRange.location`이 그린 커서를 그 UTF-16 자소 경계로 옮긴다. 논리 삽입 위치는 조합 전 텍스트 끝에 남는다. Preedit이 행 경계에서 끝나면 wrap-pending caret은 마지막 점유 cell에 그린다. 자소 안의 위치는 잘못된 값이다. Frame은 effective preedit caret과 보이는 viewport의 논리 행 origin을 보고한다. Internal engine cursor는 그대로 둔다. `screen.cursor.row`와 `.col`은 screen hash가 사용하는 raw 값을 유지하고, 필수 `screen.cursor.caret`은 frame과 같은 layout에서 계산한 화면 좌표 visible caret을 전달한다. 글리프 진행 폭이 두 셀보다 좁은 넓은 문자(예: 대체 글꼴로 그린 한글)는 자기 크기로 두 셀의 가운데에 그린다. 셀 폭 이상인 글리프는 첫 셀에서 시작한다.

정책은 터미널 플러그인이 `plugin.json`에서 선언하고, 애플리케이션의 초기 값을 `environment.json`에서 받으며, 그다음 유효한 공통/프로젝트 설정을 따른다. workbench는 저장하기 전에 각 값을 선언과 대조하고, 마운트된 터미널 표면에 유효한 플러그인 로컬 설정을 알리며, 값이 잘못되면 부분 패치를 적용하지 않고 명시적 오류를 보고한다. 터미널 표면은 시작할 때와 유효한 설정이 바뀔 때마다 완전한 정책을 사이드카에 보낸다.

터미널 프로그램의 클립보드 접근은 사용자의 명시적 붙여넣기와 별개다. 선언된 `clipboard.program` 설정은 `deny` 또는 `allow`이며 기본값은 `deny`다. 거부되면 OSC 클립보드 저장/조회 요청은 관찰 가능한 정책 오류를 내고, 호스트 클립보드에 쓰지 않으며, 대기 중인 조회 콜백을 남기지 않는다. 허용되면 선언된 텍스트 클립보드 대상만 처리한다. 지원하지 않는 선택 대상과 없거나 텍스트가 아닌 값은 명시적 오류로 남는다. 사용자의 `terminal.paste` 명령은 이 프로그램 권한의 적용을 받지 않는다.

네이티브 IME가 표시 중인 텍스트를 소유한다. 조합 중인 텍스트는 부분 음절을 PTY에 쓰지 않고 표시한다. 확정된 텍스트는 보통 입력과 같은 순서 있는 큐로 정확히 한 번 전달된다. 각 네이티브 입력 report는 순서 있는 action과 필수 최종 preedit snapshot을 담은 하나의 `input` transaction이다. Surface actor는 transaction 전체를 부작용 전에 검증하고, 쓰기를 만드는 action을 한 번의 순서 있는 PTY write로 적용하며, 최종 preedit을 한 번 적용한다. 이미 준비된 PTY output은 최종 frame 전에 반영하고 action별 중간 frame은 제출하지 않는다. 각 네이티브 입력 report는 순서 있는 action과 필수 최종 preedit snapshot을 담은 하나의 `input` transaction이다. Surface actor는 부작용 전에 transaction 전체를 검사하고, 순서 있는 action 바이트를 한 actor transition에서 쓰고, 최종 preedit을 한 번 적용하며 action별 중간 frame을 제출하지 않는다. action이 없는 compose-only report도 유효하다. PTY echo는 기다리지 않으며, 자식이 echo하지 않은 바이트가 cursor나 committed screen에 반영된다고 보장하지 않는다. image 전송 대기 중 PTY echo가 도착하면 이후 frame은 결과 preedit snapshot을 사용하고 같은 입력 문서 텍스트를 확정 셀과 preedit으로 두 번 그리지 않는다. 캐럿 좌표는 후보 창을 고정한다. 지원하지 않는 네이티브 텍스트 값과 실패한 입력 동작은 명시적 오류다.

각 네이티브 preedit 레코드는 필수 `markedRange`를 가지며, 값은 `null` 또는 `text` 기준 UTF-16 코드 단위의 `{location, length}`다. Core producer가 실제 AppKit marked range를 전달한다. Sidecar는 editable text suffix, `selectedRange`, `replacementRange`, `attributed`에서 이를 추정하지 않는다. null 또는 길이 0 범위는 어떤 preedit grapheme에도 밑줄을 그리지 않는다. 비어 있지 않은 범위는 그 범위가 덮는 grapheme에만 밑줄을 긋는다. Sidecar는 누락 또는 잘못된 형식, 음수 또는 overflow 범위, `text`의 UTF-16 길이를 넘는 끝점, grapheme 내부의 끝점을 이름 있는 오류로 거부한다. `selectedRange`는 선택 배경과 cursor를 계속 독립적으로 제어한다. 필수 필드이며 service는 이전 preedit 형식을 읽지 않는다. Message envelope는 protocol 1을 유지한다. 이 필드는 설치되거나 다시 읽는 화면 형식을 바꾸지 않으며, preedit는 활성 service surface 상태에만 존재한다.

Preedit은 하나의 논리적 줄이며 화면 cursor에서 시작해 terminal cell을 차지한다. 표시 셀은 terminal 열 수에 따라 다음 행으로 이어진다. 두 칸 너비 grapheme이 남은 열에 들어가지 않으면 그 grapheme 전체를 다음 행의 첫 칸으로 옮기며, 마지막 열에서 grapheme을 나누지 않는다. 열이 한 개인 grid에서는 두 칸 grapheme을 0열에 놓고 기존 image 경계에서 raster pixel을 자른다. Combining grapheme은 배치 중에도 base grapheme에 붙어 있다. Renderer는 완전한 논리적 preedit을 screen 복사본에 덮어 그린다. Overlay가 기존 넓은 grapheme의 어느 한 cell에 닿으면 복사본에서 기존 span 전체를 지우고 preedit을 그리며 확정 cell을 옮기지 않는다. Overlay가 덮지 않는 행의 screen 복사본 내용은 유지한다. PTY, 확정 screen 상태, 입력 text는 바뀌지 않으며 preedit을 지우면 변경되지 않은 base screen을 다시 그린다. `markedRange`와 `selectedRange`는 원래 `text`의 UTF-16 범위로 유지한다. 밑줄, selection background, caret은 wrap을 포함한 동일한 grapheme-to-cell 배치를 사용한다. 다음 행으로 이동한 grapheme 앞의 boundary는 그 행 0열에 놓인다. 전체 preedit 끝의 boundary가 행을 정확히 채운 경우에는 wrap-pending caret으로 처리한다. UTF-16 범위는 text 끝에 남기고 보이는 caret은 빈 다음 행으로 이동하지 않고 마지막 점유 cell에 둔다. 열이 하나인 grid에서 잘린 두 칸 grapheme의 끝 caret은 0열에 둔다. `selectedRange.location`이 없으면 engine cursor가 viewport anchor이고 보이는 행 origin은 0이다. selected 위치가 있으면 그려질 caret을 변환하고 보이도록 가장 작은 0 이상의 viewport origin `max(0, paintedCaretRow - (screen.rows - 1))`을 선택한다. Renderer는 고정된 높이 viewport 밖의 논리 preedit 행을 화면에서 자르지만 preedit state를 바꾸거나 자르지 않는다. Frame metadata는 `grid.logicalRowOrigin`과 effective caret 사각형을 보고한다. Internal engine cursor와 PTY 행은 유지한다. `screen.cursor.row`와 `.col`은 screen hash가 사용하는 raw engine 값을 유지하고, 필수 `screen.cursor.caret`은 frame과 같은 layout의 화면 좌표 visible caret을 제공한다. Glyph `width`는 grid 안에 보이는 cell span이다. Ink bounds는 실제 draw의 raw bounds이며 cell 또는 raster 경계를 넘을 수 있다.

Native IME는 marked text를 소유한다. 각 native input report는 순서 있는 action과 필수 최종 preedit snapshot을 담은 하나의 `input` transaction이다. Surface actor는 transaction 전체를 부작용 전에 검증하고, 쓰기를 만드는 action을 한 번의 순서 있는 PTY write로 적용하며, 최종 preedit을 한 번 적용한다. 이미 준비된 PTY output은 최종 frame 전에 반영하고 action별 중간 frame은 제출하지 않는다. 앞으로 도착할 PTY echo는 기다리지 않으며 child가 아직 echo하지 않은 바이트에 맞춰 cursor나 committed screen을 갱신한다고 보장하지 않는다.

네이티브 입력 어댑터는 텍스트 입력 클라이언트의 표시 중 텍스트 콜백으로 조합 중 입력과 확정 입력을 구분하며, 유니코드 범위를 검사해서 구분하지 않는다. 예외는 아래의 macOS 한국어 입력기의 확정 시점뿐이다. 모든 `insert` 콜백은 순서대로 바이트 그대로 전달된다. 플러그인은 문자 체계나 코드 포인트를 근거로 그것을 조용히 버리거나 다시 쓰면 안 된다. 플랫폼 어댑터는 OS 텍스트 입력 수명 주기를 써야 하며, 확정된 각 콜백을 정확히 한 번 드러내야 한다. 빈 `compose` 콜백은 조합 중 텍스트를 지우거나 취소하며, 이전 표시 문자열을 확정하지 않는다. 오직 `insert` 콜백만 PTY에 텍스트를 확정한다. 플랫폼이 표시 중 텍스트를 입력으로 받아들이면(macOS에서는 `unmarkText`), 어댑터는 그 텍스트를 `insert` 하나로 보고한다.

입력기는 표시 중 텍스트 대신 앞서 자기가 넣은 텍스트를 고칠 수 있다. 예를 들어 macOS 한국어 입력기는 `ㅎ`을 넣은 뒤 교체 범위로 그것을 `하`와 `한`으로 바꾸며, 자기가 조합 중인 음절의 문서 위치를 기억한다. 그래서 키보드 배열이 아니라 입력기가 선택된 동안, 플랫폼 어댑터는 입력기가 넣은 텍스트를 자기 입력 문서에 보관하고, 교체를 그 문서에 적용하며, 입력기가 아직 고칠 수 있는 부분을 조합 중 텍스트로 보고한다. 가장 최근 `insert`의 시작 전 텍스트는 `insert` 하나로 확정된다. 확정된 텍스트는 입력 문서에 남으므로 위치가 바뀌지 않는다. macOS 한국어 입력기는 한글 자모와 음절만 조합하며, 이 교체 프로토콜에서는 조합이 끝날 때 콜백을 보내지 않는다. 음절 뒤의 Space나 숫자는 음절과 한글이 아닌 문자를 편집 가능한 접미부에 남길 수 있다. 앞에 관찰된 콜백은 음절을 그 자신으로 바꾼 뒤 Space나 숫자를 넣었다. 이 입력기는 마지막 자음이 다음 음절로 넘어갈 때 최근 `insert` 앞의 음절을 고치기도 하고, 그것을 바꾸기 전에 새 음절을 덧붙이기도 한다. 그래서 선택된 동안 어댑터는 다음 `insert`나 조합 끝까지 그 한글 음절을 편집 가능한 접미부에 둔다. 이 입력기가 선택된 동안 어댑터는 편집 가능한 접미부의 마지막 문자가 한글이 아니면 그 접미부를 즉시 확정한다. 이것은 마지막 음절과 Space가 한 접미부에 있을 때를 다루며, 새 한글 자모는 조합 중 텍스트로 남는다. 이 규칙은 텍스트를 언제 확정할지만 정한다. 입력은 버려지거나 바뀌지 않는다. 다른 입력기는 일반 규칙을 따른다. 확정되지 않은 입력기 텍스트가 있는 동안, Control이나 Option이 없는 특수 키는 먼저 입력기로 간다. 그래서 Backspace는 텍스트 보기에서처럼 조합을 편집한다(`한`이 `하`가 된다). 입력기가 그 키를 처리하지 않으면 AppKit은 클라이언트에 그 키의 명령 수행을 요청하고, 어댑터는 남은 텍스트를 확정한 뒤 명령 대신 원래 키를 보고한다. AppKit이 `insertNewline:`을 호출해 Enter를 처리하면, 터미널 입력 경로는 확정된 텍스트 뒤에 Enter 키 하나를 보낸다. AppKit의 `noop:` 선택자는 명령에 효과가 없으므로 입력을 바꾸거나 확정하지 않고 로컬에서 소비한다. 지원하지 않는 다른 네이티브 명령 선택자는 명시적으로 보고된다. 다른 특수 키, 명령, 포커스 상실, 입력 소스 변경, 영역 닫기 전에는 어댑터가 남은 텍스트를 확정하고, 입력기의 조합을 끝내고, 문서를 지운다. 키보드 배열의 텍스트는 즉시 확정된다. 이미 확정된 텍스트의 교체는 명시적 오류다. 어댑터는 입력 문서를 텍스트 저장소로 가지는 AppKit 텍스트 뷰다. 터미널이 선언하지 않은 텍스트 시스템 편집은 모두 끈다. 자동 치환, 대체, 맞춤법과 문법 검사, 감지, 자동 완성, 텍스트 검사 종류, 실행 취소, 리치 텍스트, 그래픽, 찾기 막대, 글꼴 패널, 눈금자가 여기에 든다. 서비스 메뉴는 입력 문서를 읽거나 바꿀 수 없고, 포인터, 메뉴, 드래그 입력은 뷰를 대상으로 하지 않는다. 자기 문서를 가진 일반 뷰도 같은 한국어 결과를 냈지만, 입력 클라이언트로서 영역이 닫힌 뒤 해제된 메모리를 계속 쓰게 만들었으므로 텍스트 뷰를 유지한다.

터미널 플러그인은 `diagnostics.json`에서 `terminal.compose.update`를 선언한다(호스트 플러그인 계약의 진단 선언). 그래서 이 명령은 진단 빌드에서만 존재한다. 이 명령은 OS 입력기가 만들 조합 중 텍스트를 주입한다. 네이티브 콜백과 같은 순서 있는 사이드카 경로로 현재 조합 상태를 명시적으로 정하기 위한 것이다. 문자열 `text`, 선택적 `selectedRange`와 `replacementRange`(`null` 또는 0 이상 정수 `{location, length}`), 선택적 불리언 `attributed`를 받는다. 범위가 없으면 `null`, `attributed`가 없으면 `false`다. 빈 문자열은 조합 중 텍스트를 지운다. 이 명령은 PTY 바이트를 쓰지 않는다. 기존 `terminal.compose` 상태는 유효한 조합 중 텍스트를 보고하며, 네이티브 그림은 허용된 각 갱신을 앞의 그림 전송이 consumed된 뒤에 보인다. 이 명령은 조합 중 텍스트 렌더링과 순서를 검증한다. 실제 OS IME 검증을 대신하지 않는다.

터미널 플러그인은 `terminal.ime.trace` 명령과 상태를 통해, 명시적으로 시작하고 용량이 제한된 IME 진단 추적도 제공한다. 이 추적은 `diagnostics.json`에서 선언한다. 켜져 있는 동안 네이티브 `key`, `compose`, `insert` 콜백과 각각에 대응하는 순서 있는 터미널 입력 동작을 기록하며, 이벤트 순서와 텍스트를 보존한다. 추적 용량에 도달하면 추적은 눈에 보이게 실패하며, 이벤트를 조용히 버리지 않는다. 추적을 멈추면 항목과 초과 상태를 돌려준다. 추적은 기본적으로 꺼져 있고, 진단 증거일 뿐 네이티브 픽셀 조합 검사를 대신하지 않는다.

선택, 클립보드, 붙여넣기, 파일 놓기, 이미지 붙여넣기, 터미널이 만든 이미지 표시는 서로 다른 동작이다. 붙여넣은 이미지는 소유된 파일로 저장되며, 그 경로는 자동 실행 없이 삽입된다. 선언된 `terminal.paste` 명령이 유일한 텍스트 붙여넣기 진입점이다. 편집 > 붙여넣기(Command+V)와 포커스된 터미널 영역의 서식 맞춰 붙여넣기는 `paste` 동작을 보고하고, 이것은 명령 레지스트리를 통해 `terminal.paste`를 실행한다. 편집 > 복사(Command+C)는 `copy` 동작을 보고하고, 이것은 `terminal.copy`를 실행한다. `terminal.copy`는 `copy` 요청을 보내며, 사이드카는 현재 선택 텍스트를 담은 `copy` 이벤트로 답한다. 터미널 모듈은 그 텍스트를 `userInitiated: true`로 클립보드에 쓴다. 선택이 없으면 `copied: false`로 답하며, 클립보드는 바뀌지 않는다. 영역은 클립보드 내용을 입력 문서에 결코 넣지 않으며, 잘라내기, 전체 선택, 삭제는 영역에서 비활성이다. 명령은 범위가 있는 클립보드 권한을 통해 `userInitiated: true`로 텍스트 클립보드를 읽고, 없거나 텍스트가 아닌 내용은 명시적으로 거부하며, `paste` 동작 하나를 사이드카에 보낸다. 선택 해제의 복사가 사이드카에서 아직 오는 중이면(사이드카는 해제를 보여 주는 래스터 뒤에 그것을 보낸다) 명령은 그것을 기다린다. 그래서 해제 뒤의 붙여넣기는 그 선택의 텍스트를 돌려준다. 클립보드 실패를 빈 입력으로 바꾸지 않는다. 괄호 붙여넣기는 터미널 모드를 따르고, 제공된 UTF-8 내용을 바이트 그대로 보존하며, 내장된 괄호 붙여넣기 종료자를 지우는 대신 거부한다. 사이드카는 전체 내용을 한 번 쓴 뒤에만 동작을 확인한다. 입력은 조용히 정리되거나 버려지거나 재정렬되지 않는다. 터미널 프로토콜 지원은 수열과 참조 개정별로 기록한다. 구문 분석기가 받아들인다는 이유로 구현되지 않은 동작을 지원하는 것으로 세지 않는다.

터미널 위의 휠 입력은 스크롤 제스처다. 터미널 페이지는 뷰의 DOM 휠 증분을 온전한 줄로 바꾼다. 픽셀 증분은 셀 높이로 누적한다. 그리고 `{operation: "scroll", lines, col, row, shift}`를 보낸다. 양의 `lines`는 오래된 출력 쪽으로 움직이며, `col`과 `row`는 포인터의 셀이고, `shift`는 Shift를 누르고 있는 동안 true인 선택적 boolean이다. `shift`가 없으면 Shift가 없는 scroll이므로, `shift`를 보내지 않는 page의 operation은 `false`를 보낸 것과 같다. 있는 `shift`가 boolean이 아니면 `invalidParams`로 거부한다. 사이드카는 터미널 모드와 `shift`에 맞는 첫 규칙을 적용한다. 마우스 보고(모드 1000, 1002, 1003)가 켜져 있고 `shift`가 false이면, 줄마다 휠 버튼 이벤트 하나를 쓴다(오래된 출력 쪽은 버튼 64, 최신 쪽은 65). 이것은 포인터 셀에서 활성 마우스 인코딩(SGR 1006, UTF-8 1005, 또는 기본값)으로 쓴다. 그렇지 않고 대체 화면에서 대체 스크롤(모드 1007)이 켜져 있으면, 현재 커서 키 모드로 줄마다 커서 위 또는 아래 키 하나를 쓴다. 그 밖에는 주 화면의 뷰포트를 `lines`만큼 스크롤백을 따라 움직이되, 보존된 기록 안으로 제한한다. 화면 이벤트는 뷰포트를 보여 주며, 커서는 그 행이 뷰포트 밖이면 숨겨진 것으로 보고된다. 키보드 입력, 텍스트 입력, 붙여넣기는 바이트를 쓰기 전에 뷰포트를 최신 출력으로 되돌린다. `terminal.session`은 `scrollback: {offset, history}`를 보고한다. `offset`은 뷰포트가 최신 출력 위로 있는 줄 수이고, `history`는 보존된 기록 줄 수다. 선택 좌표는 제스처가 일어날 때의 뷰포트 좌표다. 서비스는 마우스 모드가 바뀔 때마다 이벤트 `sidecar.vt.mouse_modes`(class `lifecycle`, level `info`)를 기록하고, scroll operation마다 이벤트 `sidecar.vt.wheel`(class `input`, level `info`)을 기록한다. `sidecar.vt.wheel`에는 경로 `route`(`program`, `alternate_scroll`, `viewport`), `lines`, `col`, `row`, `shift`와 그 시점의 모드 `mouse_click`, `mouse_drag`, `mouse_motion`, `sgr_mouse`, `utf8_mouse`, `alternate_scroll`, `alt_screen`이 담긴다.

터미널이 기록(`scrollback.history`가 0보다 큼)을 보존하는 동안, 터미널 페이지는 뷰의 오른쪽 가장자리에 선언된 DOM 오버레이 `scrollbar`로 스크롤바를 보인다. 이 오버레이는 네이티브 그림 위에 있다. 최신 출력에서는 엄지 부분이 트랙의 아래에 있다. 트랙은 터미널의 현재 기본 배경으로 칠해지며, 화면 이벤트는 그것을 `background`로 보고한다(OSC 11에 의한 변경 포함). 호스트가 오버레이 아래의 네이티브 그림을 잘라 내기 때문이다. 엄지의 높이는 트랙 높이에 `rows / (rows + history)`를 곱한 값이며 최소 16포인트다. 엄지의 위쪽은 트랙의 `(history - offset) / (rows + history)` 위치다. 엄지 위의 포인터는 열린 손이며, 엄지를 끄는 동안은 쥔 손이다. 엄지를 끌면 포인터 아래의 오프셋을 담아 선언된 `terminal.scrollback.set` 명령을 실행한다. 이것은 `{operation: "viewport", offset}`을 보낸다. 사이드카는 주 뷰포트를 그 오프셋으로 옮기되, 보존된 기록 안으로 제한하며, 프로그램에는 아무것도 쓰지 않고 화면 이벤트로 답한다. 기록이 없으면 스크롤바는 숨겨진다. 네 개의 플러그인 설정이 그것을 구성한다. `terminal.scrollbar.track`은 `terminal`(터미널의 현재 기본 배경, 기본값) 또는 색이다. `terminal.scrollbar.thumb`은 엄지 색이다(기본값 `#8f98a080`). `terminal.scrollbar.width`는 4에서 24 사이의 포인트 단위 트랙 너비다(기본값 10). `terminal.scrollbar.shape`은 `rounded`(기본값) 또는 `square`다. 색은 `#rrggbb` 또는 `#rrggbbaa`다. 그 밖의 값은 입력 오류로 보고되고 적용되지 않는다. 변경은 보이는 스크롤바에 바로 적용된다.

플러그인 설정 네 개가 터미널 여백을 정한다. `terminal.padding.top`, `terminal.padding.right`, `terminal.padding.bottom`, `terminal.padding.left`는 0에서 64 사이의 포인트 단위 정수다(기본값 0). 페이지는 네이티브 그림 영역 `view`를 이 값만큼 안쪽으로 밀므로, 셀 격자는 여백 안쪽 영역을 차지한다. 스크롤바는 그 영역의 오른쪽 가장자리에 둔다. 네이티브 앵커의 조상은 배경이 없으므로(호스트의 표면 구성), 각 쪽의 여백은 선언된 DOM 오버레이 띠(`padding-top`, `padding-right`, `padding-bottom`, `padding-left`)이며, 터미널의 현재 기본 배경으로 칠한다. 크기가 0인 띠는 숨긴다. 그 밖의 값은 입력 오류로 보고되고 적용되지 않는다. 변경은 즉시 적용된다.

터미널 선택은 DOM 텍스트 선택이 아니라 네이티브 영역의 제스처다. 네이티브 영역은 왼쪽 버튼 누름, 이동, 놓음을 CSS 로컬 좌표와 수정 키 상태와 함께 보고한다. 사이드카는 그 좌표를 설정된 셀 격자에 대응시키고, 선택 상태를 소유한다. 이동은 왼쪽 버튼을 누른 채의 포인터 이동이다. 버튼 없이 하는 이동, 예컨대 창이 키 창이 될 때 WebKit이 보고하는 포인터 위치는 선택을 시작하거나 갱신하지 않는다. 뷰 안의 누름 뒤에, 페이지는 뷰 밖의 드래그 점을 뷰 안의 가장 가까운 점으로 옮긴다. 줄의 시작이나 끝으로 드래그하면 뷰 가장자리를 넘기 때문이다. 뷰 밖의 누름은 선택을 시작하지 않는다. 사이드카는 누름과 각 드래그 점을 그 행의 가장 가까운 셀 가장자리에 대응시킨다. 그래서 포인터가 셀의 가로 중점을 지나면 그 셀이 선택에 든다. macOS 터미널처럼 드래그 방향과 관계없이, 선택은 두 가장자리 사이의 셀을 덮는다. 렌더링된 선택은 복사되는 텍스트의 셀과 정확히 같은 셀을 덮는다. 영역은 마지막 온전한 열과 행을 한 셀보다 적게 넘어 확장된다. 그 여백의 점은 마지막 행과 가장 가까운 가장자리에 대응하며, 마지막 열을 넘는 경우 그 오른쪽 가장자리가 된다. 호스트는 네이티브 영역의 가장자리를 장치 픽셀에 맞추므로, 영역은 뷰보다 최대 한 장치 픽셀 작을 수 있다. 그래서 영역을 한 장치 픽셀보다 덜 넘는 점은 여백의 점처럼 대응한다. 영역에서 더 멀리 떨어진 점은 잘못된 좌표다. 일반 드래그는 단순 선택을 만들고, 렌더링된 선택 픽셀을 갱신하며, 놓을 때 선택된 텍스트를 담은 명시적 사용자 선택 복사 이벤트를 하나 낸다. 터미널 모듈은 그 텍스트를 `userInitiated: true`로 범위가 있는 클립보드 권한을 통해 쓴다. `clipboard.program` 정책은 이 사용자 제스처를 거부하지 않는다. 텍스트가 없는 선택의 놓음(예: 빈 셀 위의 드래그)은 선택을 지우고, 클립보드는 그대로 두며, `copied: false`로 `selection.end`를 낸다. 이것은 정상 제스처이며 오류가 아니다. 움직임 없는 누름과 놓음(클릭)이나, 셀의 중점을 지나지 않는 드래그는 한쪽 가장자리에서 빈 선택을 시작하고 끝낸다. 그래서 클릭은 이전 선택을 지운다. `terminal.session`은 왼쪽 버튼 제스처가 진행 중이면 `selecting`을 보고하며, 사이드카가 복사나 `selection.end`로 답한 놓음의 수를 `selectionReleases`에 센다. 클립보드 권한이 없음, 잘못된 좌표, 텍스트 없는 복사 이벤트, 실패한 쓰기는 명시적 오류다. 선택 입력은 PTY에 결코 보내지 않으며 DOM 대체 경로를 쓰지 않는다.

페이지는 왼쪽 버튼의 모든 누름, 누른 채의 이동, 놓음과, 버튼 없이 다른 셀에 들어가는 이동도 `mouse` 동작 `{phase, x, y, pressed, shift, alt, ctrl}`로 보낸다. 프로그램이 마우스 보고를 켰으면, Shift 없는 누름은 보고되는 제스처를 시작하고 이전 텍스트 선택을 지운다. 사이드카는 누름에서 그 제스처의 이동 소유권을 고정한 뒤, 누름, 놓음, 그리고 고정된 소유권에 ?1002나 ?1003이 들어 있으면 누른 채 다른 셀로 들어가는 각 이동을 쓴다. 드래그 중의 자식 마우스 모드 변경은 텍스트 선택으로 소유권을 옮기지 않는다. 그 제스처의 선택 동작은 아무것도 선택하지 않으며 보통처럼 답한다. ?1003이면 버튼 없이 다른 셀로 들어가는 이동도 보고된다. 받아들여진 포인터 단계마다 `mouse` 이벤트를 내고, `terminal.session.mouse`를 단계, 셀, 수정 키, 활성 보고 모드, PTY 보고가 선택되었는지, 쓰기 결과, 있으면 정확한 base64 PTY 바이트로 갱신한다. 보고되지 않은 단계는 버리지 않고 `reported: false`와 `bytes: null`로 낸다. 이것은 자식 프로그램이 제스처를 받았는지 재는 측정 원천이다. 보고 형식은 기본 인코딩, ?1005의 UTF-8 좌표, ?1006의 SGR을 쓰며, Alt(8)와 Control(16) 비트를 싣는다. 기본 인코딩이 나타내지 못하는 좌표는 명시적 오류다. Shift를 누른 누름은 마우스 보고가 켜져 있을 때 텍스트를 선택한다. 터미널 뷰는 OSC 22 포인터 모양이나 링크가 바꾸지 않는 한, 래스터 텍스트 위에서 텍스트 선택 포인터를 쓴다. 느린 이동이 잠깐이라도 화살표 포인터를 보여서는 안 된다. 영역은 왼쪽 버튼만 보고한다. 프로그램이 포커스 보고(?1004)를 켰으면, 영역이 네이티브 포커스를 얻을 때 사이드카는 `ESC[I`를, 잃을 때 `ESC[O`를 쓴다. 변경마다 한 번이다. 영역은 숫자 키패드 키를 입력기에 넘기지 않고 이름(`Keypad0`–`Keypad9`, `KeypadDecimal`, `KeypadPlus`, `KeypadMinus`, `KeypadMultiply`, `KeypadDivide`, `KeypadEquals`, `KeypadEnter`)으로 보고한다. `ESC =` 뒤에 사이드카는 수정자가 없는 키패드 키를 `ESC O`와 `p`–`y`, `n`, `k`, `m`, `j`, `o`, `X`, `M` 중 하나로 보낸다. 그 밖에는 키의 문자나 캐리지 리턴을 보낸다.

### 터미널 세션 오류

`terminal.session.error`는 표면의 가장 최근 미해결 오류다. 플러그인은 원천마다 가장 최근 오류를 유지하며, 한 원천의 이벤트는 다른 원천의 오류를 지우지 않는다. 스냅샷 원천은 같은 종류의 다음 유효한 이벤트로 해결된다. 다른 원천은 표면이 닫힐 때까지 남는다. 실패한 동작이 성공했음을 보여 주는 이후 이벤트가 없기 때문이다.

| 원천 | 오류 | 해결되는 시점 |
| --- | --- | --- |
| `state` | 잘못된 `state` 이벤트 | 다음 유효한 `state` 이벤트 |
| `session` | 잘못된 영속 `session` 이벤트 | 다음 유효한 `session` 이벤트 |
| `theme` | 잘못된 테마 확인 응답 | 다음 유효한 `theme` 이벤트 |
| `screen` | [화면 메시지](https://github.com/soksak-app/core/blob/main/docs/spec/persistent-services.ko.md#화면-메시지)가 거부하는 `screen` 이벤트(잘못된 커서나 해석된 색이 없는 셀 등) | 다음 유효한 `screen` 이벤트 |
| `trace` | IME 추적 용량 초과(진단 빌드) | 새 추적 시작 |
| `sidecar` | 사이드카의 `error` 이벤트 또는 오류 응답. 응답은 거부된 동작을 이름으로 밝히지 않는다 | 해결되지 않음 |
| `native image` | 네이티브 그림 영역의 `error` 이벤트 | 해결되지 않음 |
| `input` | 실패한 입력, 붙여넣기, 클립보드, 선택 동작과 잘못된 일회성 사이드카 이벤트 | 해결되지 않음 |
| `key` | 불리언이 아닌 수정자를 가진 네이티브 키 이벤트 | 해결되지 않음 |
| `cursor` | 사이드카의 잘못된 커서 위치 | 해결되지 않음 |

`sidecar`와 `native image` 원천은 카드가 보여 주는 표면 오류도 보고한다. 둘 다 해결되지 않으므로, 카드 표시와 `terminal.session.error`는 표면이 닫힐 때까지 그 오류를 보여 준다.

### Frame clock

surface는 session 출력을 33 ms frame clock으로 그린다. 마지막 frame 뒤 33 ms가 지나기 전에 온 변경은 33 ms가 지났을 때 그 구간의 다른 변경과 함께 그리고, 더 긴 멈춤 뒤에 온 변경은 바로 그린다. cursor blink도 같은 clock을 따른다. `input`이나 `paste` 요청 뒤 200 ms 동안은 출력을 바로 그리므로 타이핑의 echo가 기다리지 않는다. 변경이 없는 clock tick은 frame을 그리지 않는다. frame 기록은 clock의 frame을 reason `clock`으로 적는다.

### Strip frame

session의 image surface는 `Frame::new_strip`이 만든 frame으로 그린다. render metadata를 모으는 diagnostic build(`SOKSAK_VT_TRACE_DIR`)는 CoreGraphics frame으로 그린다. render metadata를 보고하는 frame이 그것뿐이기 때문이다. 두 frame 모두 CPU로 그린다. strip frame의 pixel은 같은 화면의 CoreGraphics frame과 같으므로, CoreGraphics frame이 두 그리기의 유일한 기준이다.

- frame은 strip surface에 화면 행마다 strip 하나를 둔다. strip은 CoreGraphics frame의 칸 loop가 그리므로, 글자, 넓은 글자, 밑줄, 그리고 `render_layout`이 칸에 넣은 preedit을 한 함수가 그린다. strip은 행의 hash가 그 strip을 그린 hash와 다를 때만 다시 그린다. 크기, 글꼴, theme이 바뀌면 모든 strip을 다시 그린다. 그래서 frame의 그리기 비용은 바뀐 행에 비례한다.
- 두 frame 모두 각 행을 그 행의 box로 자르므로, 행 위아래로 넘친 잉크는 그 행 안에서만 그린다.
- strip은 행 아래 여백의 기본 배경도 담는다. CoreGraphics 그리기는 CoreGraphics frame의 `CGContextDrawImage` 호출로, 각 image 아래 strip pixel을 복사한 overlay surface 위에 inline image를 합성한다. 그리기는 strip을 target surface로 복사한 뒤 overlay의 image 사각형을 복사하고, CoreGraphics frame의 채우기와 difference 채우기로 cursor를 그린다. 그래서 글자나 image 위의 block cursor는 그 pixel을 반전한다.
- CoreGraphics가 투명한 surface에 그리고 나중에 합성하는 image tile은 CoreGraphics frame과 다르다. 반투명 test image에서 pixel이 최대 두 단계 달랐고, 그중 34개는 image가 불투명한 곳이었다. CoreGraphics가 투명한 surface 위와 덮는 pixel 위에서 image를 다르게 resampling하기 때문이다. overlay는 각 image를 CoreGraphics frame과 같은 pixel 위에 그리므로 구성상 정확하다.
- 그리기는 동기적이다. target surface가 frame을 담은 뒤 돌아오므로, supplier는 마지막 쓰기 뒤에 envelope를 보낸다.
- 그리기는 GPU pass를 쓰지 않는다. strip 뒤에 남는 일은 이 복사와 사각형 몇 개뿐이고, Metal driver는 pass를 encode한 process에 메모리를 잡아 둔다. 1520x1228 frame에서 footprint는 blit와 render pass로 178 MB, compute pass 하나로 96 MB, Metal 없이 16 MB 늘었다. frame의 CPU 시간은 늘지 않았다. 한 행이 바뀌는 frame은 1.27 ms, 모든 행이 바뀌는 frame은 3.08 ms이고, blit와 render pass일 때는 1.24 ms와 3.43 ms였다. test가 footprint 증가에 상한을 둔다(`frame_memory_test`).
- 그리기가 다시 그린 strip 수는 진단 build의 render output에만 있다.
- 한계: scroll은 모든 행을 바꾸므로 모든 strip을 다시 그린다. CoreGraphics frame이 모든 칸을 다시 그리는 것과 같다. strip을 행 내용으로 보관할지는 개발 뒤 scroll benchmark가 정한다.

이유와, adversarial review가 제기하고 이 설계가 답한 반론:
- CoreGraphics frame은 글자를 배경에 맞춰 smoothing한다(검은 배경의 흰 글자와 흰 배경의 검은 글자에서 잉크가 있는 pixel 1176개 중 709개가 보색이 아니었다). 그래서 배경과 무관한 coverage의 atlas로는 그 pixel을 재현할 수 없고, 칸 밖에서 합성하는 칸 단위 tile은 값이 다른 둘째 renderer다.
- 자기 배경 위에 그린 칸 단위 tile은 앞 칸이 그 칸에 그린 잉크를 지우지만, CoreGraphics frame은 그것을 남긴다. 행 strip은 칸을 그리는 순서대로 담으므로 구성상 정확하다.
- 칸 배경색을 key로 하는 cache는 색마다 커진다. strip은 화면 행 수로 제한된다.
- 행 위치에 대한 반론은 거절했다. `H - (r + 1) × cell height`의 CoreGraphics 사각형은 아래쪽 원점 좌표이며 surface 메모리의 `r × cell height`부터 `(r + 1) × cell height`까지의 행을 덮고, 행 아래에 여백이 있는 test가 이를 검증한다.

### 터미널 검증

- 수정 전에 실패하는 기준선을 기록하고, 수정 뒤 같은 검사를 실행한다.
- 생성, 정상 닫기, 비정상 종료, 재연결 동안 서비스 프로세스, 셸 신원, PTY 디스크립터, 연결, 출력 순서를 잰다.
- 두 네이티브 호스트 모두에서 터미널 셋 이상을 실행한다. 구분선의 빠른 제스처 전체, 바뀌지 않는 글리프 메트릭, 네이티브 클리핑, 덮음, 복원된 영역을 캡처한다.
- 주입된 확정 문자열만이 아니라 실제 네이티브 키보드와 IME 입력을 관찰한다. 의미 상태와 표시된 픽셀을 따로 검사한다.
- 로딩, 준비, 오류를 구분해 유지한다. 준비는 세션 생성 성공만이 아니라 실제 첫 네이티브 표시를 포함한다.

각 마우스 동작과 그 결과는 같은 비어 있지 않은 `inputId`를 가진다. 잘못된 좌표처럼 실패한 마우스 동작도 마우스 결과로 답한다. 그 결과의 `x`와 `y`는 `null`이고, `error`는 `invalidParams: <이유>`이다. 그래서 결과는 짝을 유지한다. 페이지는 그 오류를 터미널 입력 오류로 보인다. 페이지는 모든 동작에 새 ID를 붙인다. 앞선 입력의 결과는 뒤의 제스처를 완료할 수 없다. `written`은 PTY 쓰기가 성공했다는 뜻이지, 자식이 바이트를 소비했거나 선택을 그렸다는 뜻이 아니다. 진단 빌드는 `terminal.pointer.trace`를 `start`와 `stop` 동작, 그리고 DOM 포인터/캡처 이벤트, 네이티브 포커스 알림, 대기 중인 마우스 동작, 결과의 제한된 순서 항목으로 드러낸다. 초과는 명시적이며 측정을 무효로 만든다. 성공한 쓰기와 자식의 수신을 구분하려고, 사이드카는 열린 세션에 대한 `pty.pending` 동작에 `{event: "pty.pending", pending, written}`으로 답한다. `pending`은 자식이 아직 읽지 않은 마스터 쓰기 입력 바이트 수이며, 플랫폼 PTY 입력 큐에서 얻는다(마스터 fd의 FIONREAD. macOS에서는 마스터와 슬레이브가 공유하는 tty를 읽는다). `written`은 세션 리더가 읽은 자식 출력 바이트의 누적 수다. 한 번의 왕복이 같은 순간의 두 값을 돌려준다. 세션이 없는 경우를 포함해 오류 응답도 같은 `pty.pending` 이벤트 표지를 실으므로, 응답이 자기 요청을 식별한다. 진단 빌드는 그 측정을 `terminal.pty.pending` 명령으로 드러낸다. 이 명령은 음이 아닌 정수 `{pending, written}`으로 결과를 내고, 명시적 사이드카 오류는 거부한다. 큐는 전송 관찰일 뿐이다. 아직 조립되지 않은 정규 모드 줄은 세지 않는다. 그래서 측정 계약은 원시 모드 자식이다. 큐가 비었다는 것은 자식에게 전달되었다는 뜻이지, 프로그램이 바이트를 해석했다는 뜻이 아니다. 두 표본 사이에서 `written`이 늘어나는 것은 자식이 출력을 만들었다는 관찰이며, 이것으로 프로그램의 구문 분석과 선택 렌더링을 나눈다.

반복 검사는 전체 화면 고정 TUI(`e2e/fixture-tui.mjs`)를 쓴다. 이 TUI는 `?1003` 움직임과 `?1006` SGR 보고를 켜고 자기 선택을 그린다. 검사는 OS 포인터 입력을 쓴다. 끌기, 같은 TUI 안의 세 번째 점 클릭, 그리고 다시 포커스하거나 상태를 재설정하지 않고 바로 다시 끌기를 한다. 실패한 뒤에만 검사는 다른 카드를 클릭해 복구를 관찰할 수 있다. 복구는 실패한 시도를 통과로 바꾸지 않는다. 각 호스트는 세 번 연속 중단 없는 주기를 통과해야 한다. 주기는 세 번째 점 영역(입력, 출력, 빈 곳)마다 하나씩이며, 가운데 주기는 느린 속도로 한다. 간헐적 실패는 반복 대상을 통해 재현하고 수용한다. 모든 제스처는 대응하는 입력 결과와 보이는 효과의 완전한 캡처 측정을 가진다. Shift 선택은 별도의 제어다.

각 명시적 flush는 앞선 기록을 쓴 뒤 자신의 FIFO marker에 응답하며 이후 flush 또는 stop marker를 소비하지 않는다.

Packaged diagnostic owner는 `SOKSAK_DIAGNOSTIC_PACKAGE_RELEASE`의 release 또는 `SOKSAK_DIAGNOSTIC_PACKAGE_DIRECTORY`의 설치된 package directory를 검사한다. Application 활성화 없이 연속 ASCII 입력을 수행하여 종료 전 supplier 기록이 disk에 도달하는지 확인하고 종료 후 승인된 모든 기록을 확인한다. 실패한 실행은 diagnostic artifact를 보존한다.

Debug event `sidecar.vt.consumed_wait`는 정확한 in-flight image identity(`name`, `generation`, `raster`, `sequence`)와 `answer`를 기록한다. `wait_us`는 image output 제출 전 시작하고 surface actor가 일치하는 응답을 처리할 때 끝나며 supplier 작업과 transport 지연을 포함한다. Nullable `queue_us`는 parsing된 응답을 surface command channel로 dispatch할 때부터 같은 처리 종료 시점까지를 측정하며 channel capacity 대기와 actor queue 대기를 포함한다. Ingress clock은 frame debug event가 켜져 있을 때만 측정하며 ingress timestamp를 수집하지 않았으면 `queue_us`는 null이다. 기본 gate는 그대로 유지하며 이 측정값으로 성능 acceptance를 입증하지 않는다.

연결의 요청은 input loop, surface actor, 또는 그 요청의 reply가 쥐고 있는 동안 진행 중이다. 도착한 지 10초 뒤에도 진행 중인 요청은 오류 event `sidecar.vt.request_waiting`이다. 이 event는 요청의 `operation`, `surface`, `cids`, `connection`, 나이 `ms`, 그리고 기다리는 단계 `stage`를 담는다. `stage`는 input loop가 처리하는 동안 `input loop`, input loop가 surface actor의 queue에 자리를 기다리는 동안 `surface queue`, 그 queue에 있는 동안 `actor queue`, surface actor가 처리하는 동안 `actor`, reply가 연결의 output queue에 자리를 기다리는 동안 `output queue`다. 응답된 요청은 기록하지 않는다. host는 `retain`과 image detach의 응답을 10초 기다리므로, 그때 진행 중인 요청은 host에서 이미 실패했다. 끝나지 않는 요청은 event를 만들지 않으므로, 연결의 watch는 가장 오래된 요청의 한도까지 잔다.

Engine event queue는 poisoning 후 mutex guard를 회수하고 기존 FIFO event를 유지한다. queue 변경은 VecDeque 삽입과 drain뿐이며 필드 간 transaction을 복구하거나 가정하지 않는다. 회수 시 유지한 event 뒤에 내부 runtime 오류 하나를 추가하고 유효한 queue를 유지한 뒤 poison flag를 지워 이후 작업에서 같은 오류를 반복하지 않는다. 서비스는 headless surface에서도 내부 runtime 오류를 구조화 오류 writer로 기록하며 program sequence rejection으로 전달하지 않는다. Alacritty callback과 neutral engine event는 같은 queue 삽입 경계를 사용한다.

PTY service는 mutex poisoning 후 공유 session registry를 유지한다. 첫 registry 접근은 회수를 구조화 오류 writer로 보고하고 회수한 guard를 보유한 채 poison flag를 지워 이후 접근에서 같은 회수 기록을 반복하지 않는다. registry 회수는 session 내부 상태의 일관성을 재구성하거나 가정하지 않는다.

연결 image transfer store는 mutex poisoning 후에도 활성 image 목록 또는 종료 상태를 유지한다. 회수는 해당 연결의 구조화 오류 writer로 한 번 보고하고 guard를 유지한 채 poison flag를 지운다. release는 계속 정확한 frame identity로 결정한다. 연결 종료는 보관 frame을 놓고 반복해도 같으며 늦은 retain이나 answer가 종료를 되돌리지 못한다.

PTY output ring과 attachment map은 mutex poisoning 후 내용을 유지한다. 첫 접근은 guard를 회수하고 session 및 필드 이름으로 구조화 오류 하나를 기록한 뒤 해당 필드의 poison flag를 지운다. replay 순서, byte 보관, attachment identity와 dropped-buffer 보고는 유지한다. 필드 회수는 sequence counter나 child 상태를 재구성하지 않는다.

PTY session 필드 회수는 closed flag, optional I/O 및 join handle, counter, 기록된 child 결과를 유지한다. 닫힌 handle을 다시 열거나 값을 재구성하지 않고 회수한 필드를 session identity와 함께 한 번 보고한다. child 완료 wait는 회수한 child guard를 유지하고 poisoning 후 기록된 완료 predicate를 계속 확인하며 wake 자체를 성공한 종료로 취급하지 않는다.
